# Releases

There are three channels: **stable** (`v0.3.0`), **beta** (`v0.3.0-beta.2`, or `-rc.1`) and **alpha** (`v0.3.0-alpha.1`). To publish, a maintainer runs **Publish release** in the Actions tab on `main`, picking the channel (and, when a new version starts, whether to raise the patch, minor or major number). It refuses a commit on which CI has not passed, works out the next version (`scripts/next-version.sh`: a version goes through its alphas, then its betas, then the release; pre-releases are numbered per channel), tags the commit and starts the release workflow on the tag. Pushing a `v*` tag by hand does the same, but the release workflow itself then checks (#207) that the tagged commit is on `main` and that CI passed on it, and fails otherwise, before it builds anything.

**Who may release is a repository setting, not a file** (a maintainer sets it up; it is not verified here): the signature that every hub trusts is `release.yml@refs/tags/<tag>`, and the workflow that runs is the one at the tagged commit, so whoever can push a `v*` tag can also edit away the checks above. Therefore: a **tag ruleset** so that only maintainers create `v*` tags and no one deletes or moves them; the **`release` environment** (the publish job uses it) with required reviewers and deployment limited to `v*` tags, so that signing waits for a person; two-factor authentication or a hardware key for every account that can do either. Until these are set, "who can push a tag" is "root on every server of the fleet" (see `docs/decisions.md`).

The release workflow has two jobs (#206): **build** (GoReleaser, `npm ci`, Go; read-only token, no `id-token`) makes the archives, packages, SBOMs and `checksums.txt`; **publish** (no install, no build) checks the files against `checksums.txt`, signs it with Sigstore and creates the release with `gh release create`. Only the second job can ask Sigstore for a certificate. GoReleaser (v2.12.0), cosign (v2.6.1) and syft (v1.57.2) are pinned to a version in `release.yml`; the actions are still referenced by tag (see `docs/decisions.md`). The release carries a GitHub Release with `tar.gz` archives, `.deb` and `.rpm` packages (linux amd64 and arm64), SBOMs, `install.sh` and `checksums.txt`, whose Sigstore signature is `checksums.txt.sigstore.json`. **Reproducible and with provenance (#215):** the binaries are built with `-trimpath` and the time of the commit (`mod_timestamp`), and the files that go into the archives and packages carry that time too, so two builds of the same tag give the same archive hashes; CI checks it on every change (`scripts/check-reproducible.sh`, job `reproducible`: two snapshot builds from a clean build cache, compared). The **publish** job also attests the build provenance of the archives and packages (`actions/attest-build-provenance`, an attestation signed with the identity of the workflow at the tag) and attaches the bundle as `provenance.sigstore.json`; check a file with `gh attestation verify <file> --repo Stellatinus/Regulus`. The hub and the helper do not check the provenance: it is for people and for tools outside Regulus, and the trust of an update is still the signature of `checksums.txt`. **The signed index of releases (#263):** a third and fourth job make and sign `latest.json` (see [Updates](updates.md)): **index** (no `id-token`, `go run ./cmd/make-latest`) writes it from the list of releases and the tag being made, **publish-index** (environment `release`, `id-token`) checks it names this tag and is not expired, signs it with the identity of this workflow at the tag and uploads it to the release. `refresh-latest.yml` starts the same workflow every Monday on the newest stable tag with `refresh_only` (no build, no release) so the index is renewed before its 21 days run out; that run waits for the approval of the `release` environment like a release does, and **a release made before `refresh_only` existed cannot be refreshed** (the workflow that runs is the one at the tag), so until the first release with this change is published, hubs find no index and say nothing. Alphas and betas are marked as pre-releases, so GitHub's **Latest** (and `releases/latest/download/install.sh`) is always the newest stable release; each release's notes start with the install command for that exact version. To verify a download:

```sh
cosign verify-blob --bundle checksums.txt.sigstore.json \
  --certificate-identity 'https://github.com/Stellatinus/Regulus/.github/workflows/release.yml@refs/tags/vX.Y.Z' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com checksums.txt
sha256sum --check --ignore-missing checksums.txt
```

## Which release can update to which

A server verifies the signature of a release with the signing identity that was current when its own binary was built (`update.Repository`). The repository moved between organizations twice in the alpha series, so:

| Installed | Signed as | Can update itself (hub or agent, from the dashboard) to |
|---|---|---|
| `v0.1.0-alpha.1`, `v0.2.0-alpha.1` | `CodexCircle/Regulus` | **nothing newer**: it refuses `v0.3.0-alpha.1` and later (the Updates page and the rollout say the signature is not valid for `Stellatinus/Regulus`) |
| `v0.3.0-alpha.1` and later | `Stellatinus/Regulus` | every later release signed as `Stellatinus/Regulus` |

A hub of `v0.2.0-alpha.1` is in the same position as an agent of it: its own update fails the same way, because both use the same check. The way out is by hand, once per server: run the installer of the new release (`install.sh --version VERSION`, see [Updates](updates.md#after-the-move-of-the-repository)), which keeps the data and, for an agent, its certificate. A rollout that includes such an agent fails for it with the signature message and stops there; the hub does not hide those servers from the list, because the version number is the only thing it knows about them.

**Moving the repository again.** Do not accept two identities at once as a permanent rule: the old organization may no longer be controlled by the maintainers, and whoever controls it could then sign releases for every server. A move needs a *bridge release* built before it: a release signed by the old identity that already accepts the new one, published and installed everywhere, and only then the first release signed by the new identity (see `docs/decisions.md`, "Signing identity across a move").
