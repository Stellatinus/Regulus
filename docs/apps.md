# Apps

**Status: design (#288), not implemented.** An **app** is third-party software (Plex, Radarr, Sonarr, TriliumNext…) that an administrator installs from the dashboard. It runs **in a container** (the decision of 2026-11-19, see [Managers, backends and apps](managers-and-apps.md)), keeps its data in a declared **volume**, and is **not** Regulus code and **not a plugin**: it needs no gRPC and no Regulus API. The container runtime is a backend of the **container manager** (Docker or Podman, #289); everything an app needs from the host (a firewall rule, a VPN, a mount) is asked of the matching **manager**, never done by the app.

## The app manifest

A manifest is a YAML file built on the **Compose specification**, so that Docker and Podman both read it, with one extra top-level key, `x-regulus`, for what Regulus needs. A manifest that Compose alone cannot read, or an `x-regulus` key it does not know, is refused.

```yaml
# apps/radarr/1.4.0/app.yaml
name: radarr                        # Compose project name; also the app id
services:
  radarr:
    image: lscr.io/linuxserver/radarr@sha256:0123…   # a digest, never only a tag
    environment:
      PUID: "{{ app.uid }}"          # values Regulus fills in
      PGID: "{{ app.gid }}"
      API_KEY: "{{ secret.api_key }}" # a secret REFERENCE, never the value
    ports: ["7878:7878"]
    volumes:
      - "{{ volume.config }}:/config"
      - "{{ resource.media }}:/media"
    restart: unless-stopped
    healthcheck: { test: ["CMD", "curl", "-f", "http://localhost:7878/ping"], interval: 30s }

x-regulus:
  id: radarr
  version: 1.4.0                     # the version of this manifest, not of Radarr alone
  title: { en: Radarr, it: Radarr }
  description:
    en: Movie collection manager.
    it: Gestione della raccolta di film.
  icon: icon.svg
  regulus: ">=0.4.0"                 # the Regulus versions it works with
  volumes:
    config: { role: configuration, size_hint: 1GiB }
    # a volume with role "data" is what removal can keep or delete
  resources:
    media: { kind: directory, access: read-write, description: { en: Where the movies are, it: Dove sono i film } }
  secrets:
    api_key: { generate: 32 }        # Regulus makes it and stores it encrypted
  permissions: [network.lan]         # what it asks the managers for
  publish: { host: radarr, port: 7878, path: / }   # a request to the reverse proxy, approved by the administrator
  limits: { memory: 1GiB, cpus: 1.0 }
  backup: { consistency: stop }      # stop | dump | snapshot, see Backup
```

Everything the app wants from the host is a **named request in `x-regulus`** that the administrator sees and approves: a *resource* (a directory, a GPU), a *permission*, a *port to open*, a *publish*. The container definition is checked by the container manager's validator, so an app that asks for `privileged`, the host network or the Docker socket is **refused as a whole** ([Managers](managers-and-apps.md#containers-289)).

**Secrets** are never in a manifest. A `secrets` entry is either generated by Regulus or entered by the administrator at install time; the hub keeps it encrypted with `secret.key` and the agent receives it in the operation that starts the app, as an environment value, and never logs it.

## The volume layout

On the server, in an **apps directory** that Regulus owns (`/var/lib/regulus-apps` by default, a setting):

```
<apps dir>/<id>/
    config/        # the volume with role configuration
    data/          # the volume with role data
    app.yaml       # the manifest as installed (a copy)
    state.json     # version, image digest, install time, the administrator's choices
```

The directory belongs to the **user the app runs as** (a dedicated unprivileged user per app, or the rootless Podman user), mode `0700`; no other app can read it. A **media library on another disk or share** is attached as a **resource**: the administrator picks an existing directory or mount, and **only that directory** is mounted into the container, with the access the manifest asked for and the administrator granted (read-only unless writing is needed). The container never gets a bigger part of the filesystem.

## The catalog

An **index** like the plugin index (#20): a signed JSON list of apps with, for each version, the URL of its manifest, its **SHA-256**, and the **Sigstore signature** of the index and of each manifest, verified with the same rules as releases ([Updates](updates.md)). Every entry has a `source` field so that other catalogs can be added later (the trust model for third parties is #23: not in the first version). **The first catalog is the project's own**, curated by the maintainers: an app is added by a pull request that adds its manifest, reviewed for the rules above, and the first apps are chosen in #301.

## Lifecycle

| Step | What happens | Audit event |
|---|---|---|
| **Install** | the administrator picks an app and a server; the dialog lists the volumes, the resources to choose, the ports and the permissions; on approval Regulus creates the directory, the secrets, pulls the image **by digest** and starts the project | `app_installed` |
| **Start, stop, restart** | operations of the container manager on the project | `app_started`, `app_stopped` |
| **Update** | a new manifest version (and image digest) is fetched; the old definition and digest are kept; the app is recreated; if it does not become healthy within its health check period (default 3 minutes) the old definition is **restored** (rollback) | `app_updated`, `app_update_rolled_back` |
| **Remove** | stops and removes the containers; the administrator chooses **keep the data** (default) or **delete it** (level 3: typed name, delay) | `app_removed` |

Every step is an audit event with a code and arguments, and each is shown on the app's page. Nothing runs without an administrator's action, except the automatic update mode below.

## Networking

The ports an app publishes are **shown to the administrator** and are never opened silently. Opening them in the host firewall is a request to the **firewall manager** (#290), approved in the same dialog, for a **local network** source. Publishing it as `https://radarr.example.org` is a request to the **reverse proxy manager** (#296), default exposure `lan`. Neither exists until its manager does; until then an app's ports are the administrator's to open.

## Updates

The **same three modes as the core** ([Updates](updates.md)): `manual` (the dashboard says a new version exists), `download` (the image is pulled, not applied; the default) and `automatic` (applied inside a maintenance window), **per app**, with a default for new apps. The check reads the catalog for a newer manifest and the registry for a newer digest of the same tag; a **new digest of an old tag is a notice, not an install**: an image that changes under the same tag is how a compromise arrives.

## Redundancy and backup

A redundant hub replicates the **definition** of an app (manifest, version, digest, choices), **never its data** ([Hub redundancy](hub-redundancy.md), #113). The data is backed up by the **backup manager** (#295): each volume with role `data` or `configuration` is included, and `x-regulus.backup.consistency` says how (`stop`, `dump` or `snapshot`). An app that declares nothing is copied as it is, and the page says that may be inconsistent.

## Relation to plugins and managers

| | Plugin (#19) | App (this page) | Manager (#287) |
|---|---|---|---|
| What it is | code that extends Regulus, talks gRPC | third-party software, no Regulus code | a system function Regulus manages |
| Runs | as a process, under the plugin supervisor | in a container | in the core and the root helper |
| Asks the host | through the permissions of its manifest | by named requests an administrator approves | is the host side |

An app that needs a host function (Tailscale, a firewall rule, a share) **asks the manager**; it does not touch the host. An app that must see Regulus (a dashboard widget, a skill for the assistant) is a plugin, not an app.

## Limits and health

Each app has **CPU and memory limits** (`x-regulus.limits`, defaults from the manifest, editable by the administrator within a ceiling), a **restart policy** (`unless-stopped` by default) and a **health check** that the container manager reads. The dashboard shows `healthy`, `starting`, `unhealthy` or `stopped` on the app's card, the last lines of its log, and its CPU and memory.

## What is decided, and why

- **Compose with `x-regulus`**, not a format of our own: both runtimes read it, and people can read and test an app by hand.
- **Image by digest.** A tag can move; the manifest pins what was reviewed.
- **No third-party catalogs yet** (#23), so the trust question is only "does this project's review hold".
- **Requests, not permissions in the file.** A manifest cannot grant itself anything: it asks, an administrator approves, the audit log records it.
