# Console and command line

Run `regulus` on the server (or `regulus console`) to open a full-screen console, in the spirit of the Claude Code and Gemini CLIs. It has five sections, reached with `tab`, the arrow keys, `1`-`5` or the mouse:

- **Status:** whether the hub runs (and the state of its systemd unit), version, uptime, the dashboard address and port (with the addresses of this machine on the network), the agent port, the data directory and database size, the configuration file, the hub's certificate that ends first (the CA, the agent listener's or an agent's), the connected agents and, when the hub has a plugins directory (`plugins_dir`), the state of each of its plugins (running, restarting, failed..., with the number of restarts and the last error). While no administrator exists it shows the one-time **setup token**, and `p` makes a one-time password reset link for the administrator (after a confirmation), so a server without a browser nearby is still manageable. The first-run screen also points to `regulus hub create-admin`, which creates the administrator from the terminal ([Authentication](authentication.md)).
- **Settings:** every setting with its description, default, current value and where the value comes from (`default`, `file`, `environment` or `dashboard`). `agent_listen` can come from the dashboard: **Servers → turn on remote agents** keeps the address in the hub's database, not in the file. While the hub runs, the console reads the address it really listens on, and a value that is in neither the file nor the environment is shown with the source `dashboard` (#423); a value set in the file or the environment would win over the dashboard's, and the dashboard could then no longer change it. When the hub is stopped the database is not read, and the row shows the file's value or empty. `enter` edits one; the text is checked as you type, `tab` cycles through the allowed choices, and `enter` writes the change into the YAML file, keeping its comments. The console says whether the hub must be restarted and offers it with `r` (`sudo systemctl restart regulus`).
- **Logs:** the last lines of the hub's log from journald, refreshed every two seconds, with a level filter on `f`.
- **Health:** the configuration is valid, the hub answers, the ports are free or served by the hub, the data directory is writable, the database exists, and no certificate ends within 90 days (a warning names the CA or agent certificates that do, and how to renew them, #128); while the hub runs, a newer release found at its last check is a warning (`updates`, #71; the install itself is on the Updates page); while the hub runs with a plugins directory, no plugin of the hub is `failed`, `incompatible` or `invalid` (a warning names them, #319).
- **Actions:** what the console can do, each with its key, what it needs and why it is not available when it is not: restart the service (`r`), reset the administrator password (`p`), turn on remote agents (`a`: writes `agent_listen: ":8443"` and restarts the hub). The keys work from every section, and each asks before doing anything. While remote agents are on it also shows what a new server needs: the hub's agent addresses and CA fingerprint (the token comes from the dashboard, **Servers → Add a server**).

The live data (agents, uptime, setup token) comes from the running hub through a Unix socket in the data directory (`regulus.sock`, mode `0600`, owned by the user that runs the hub), not through the web login. With the package install the data directory is private to `regulus`, so open the console with `sudo -u regulus regulus` to see it all, or with `sudo regulus` (changes to the configuration file need root as well). Without access to the socket the console still shows the settings and tells you what is missing.

Every screen has a scriptable equivalent that uses the same code and the same file:

| Command | What it does |
|---|---|
| `regulus status [--json\|--plain]` | the Status and Health information; exit status `0` when the hub runs, `3` when it does not, `1` when the configuration is broken |
| `regulus config list [--json\|--plain]` | every setting with value and source |
| `regulus config get KEY` | the current value of one setting |
| `regulus config set KEY VALUE [--force]` | validates and writes one setting into the configuration file (a bare port such as `9090` becomes `:9090`; `agent_listen off` turns remote agents off). The file is replaced in one step (a temporary file in the same directory, synced, renamed over it, with the same mode and owner), so a crash or a full disk leaves the old file or the new one, and two `config set` at the same time do not lose an edit. `data_dir` is refused when the current directory holds the hub's data (`regulus.db`, `secret.key`, `ca.key`) and the new one holds none, because changing the setting does not move the data and the hub would start with an empty database, a new secret key and a new CA (every enrolled agent would distrust it): copy the directory first, or add `--force` to start fresh on purpose |
| `regulus config path` | the configuration file in use |
| `regulus version` (also `regulus --version` and `regulus -v`) | prints the version on one line and exits with status `0`; the three spellings print the same text, and `regulus --help` lists them |

The file is `--config`, else `REGULUS_CONFIG`, else `/etc/regulus/config.yaml` when it exists. `config set` changes only that one line (a commented example such as `# agent_listen: ":8443"` becomes the setting) and refuses a value the hub would not accept. The settings are `listen`, `agent_listen`, `data_dir`, `builtin_agent`, `metrics_interval`, `metrics_budget`, `log.level`, `log.format` and `console.tui`.

**Turning the interactive screen off.** It is never forced. `regulus` prints the status as text instead when any of these holds, in this order (a flag beats an environment variable, which beats the configuration file, which beats detection): the flag `--no-tui` (alias `--notui`; `--tui` forces the screen on), the environment (`REGULUS_NO_TUI=1`, `CI` set, `TERM=dumb`), `console.tui: false` in the configuration file, or detection (stdin or stdout is not a terminal, such as a pipe, cron, systemd or SSH without a TTY, or the terminal is smaller than 60x16). `--json` and `--plain` print instead of opening the screen, and `--no-input` (alias `--non-interactive`) means that nothing is ever asked. `NO_COLOR` and `--no-color` only remove the colours; at start the console would ask the terminal for its background colour (to pick the light or dark palette), and a terminal that never answers costs 5 seconds, so the question is skipped when `COLORFGBG` is set, when `REGULUS_BACKGROUND=light` or `dark` says it, and on terminals that cannot answer (`TERM=linux`, `dumb`: dark), see #369; without a UTF-8 locale the console draws with plain ASCII characters. The console is in English or Italian, from the locale (`LC_ALL`, `LC_MESSAGES` or `LANG`, the first one set; `it_IT.UTF-8` is Italian); so are the text of `regulus status` and `regulus config list`. `--plain` and `--json` stay the same in every language, and the command's own usage and error messages are always in English. The reason the Settings tab gives for a refused value or a failed save follows the locale too; `regulus config set` prints the same errors in English. The strings are in `internal/console/strings.go` (English) and `strings_it.go` (Italian).

**Health and logs.** The *Network access* check (#369) says whether the dashboard can be opened from the network, as far as the machine that runs the hub can tell: `listen` on loopback is reported as local only (with the setting to change), and with a wildcard or LAN address it connects to each of the machine's addresses (`LANURLs`) to see that the hub answers there. It cannot see a firewall or a router, so it says so and gives the URL to open from another host: that last step is not verified by the console. The Logs tab follows `journalctl -u regulus -f` (the last 500 lines, then each new line, up to 2000 kept) and stops it when the tab is left; if the stream cannot start or ends it reloads the last 500 lines every two seconds as before. Logs on installs without journald are not shown: the hub has no log file setting, see #375.
