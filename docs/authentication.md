# Authentication

The hub has local accounts; each has a role, and a role is a set of permissions (see **Roles and permissions** below). Three roles are built in: `admin`, `operator` and `viewer`. On first start, with no accounts, the hub logs a one-time **setup token** (the line "no accounts yet", field `setup_token`); the dashboard asks for it together with the username and password of the first admin, so only someone who can read the hub log can claim an unconfigured hub. A new token is generated at each start until the admin exists.

- Passwords are hashed with argon2id (at least 10 characters). Login creates a session of 7 days stored in the database (only the SHA-256 of the token); the cookie is `HttpOnly`, `SameSite=Lax` and `Secure` when the request came over HTTPS (directly or via `X-Forwarded-Proto`). POST requests must be JSON from the same origin.
- **Limit on failed attempts** (`internal/auth/limit.go`): 10 failures in 15 minutes per client address, where an IPv6 address counts as its `/64` (one subscriber owns that many addresses), and 30 per account name over all addresses (so one password cannot be guessed from many addresses either). Further attempts get `429` for the rest of the window, even with the right password. The attempt is **reserved before the password is checked**, so a burst of parallel requests cannot all pass the check; a good login gives its own attempt back but does not erase the failures already made from that address; a wrong password counts, an error of the server does not. The table of counters holds at most 10,000 keys. The same limit covers second-factor codes, reset links and password changes. Only 4 passwords are hashed at the same moment (argon2 uses 19 MiB each); a request that cannot get a slot within 5 seconds gets `503` with `Retry-After`. The dashboard's sign-in, code and setup forms show these answers in the user's language: a `429` says how many minutes to wait (from `Retry-After`), and after a `503` the form tries again by itself after `Retry-After` seconds, up to three times. At the code step a `401` carries `code: invalid_code` or `code: login_expired`, so the form can say which one it was without reading the English text. Behind a reverse proxy set `trusted_proxies` (see below), or all clients share the proxy address and anyone who reaches the proxy can lock every user out; the limit still lives in the hub, so rate limiting in the proxy as well is a good idea. The limit lives in memory: a restart of the hub clears it. If an account is locked by someone else's guesses, wait out the window, restart the hub, or reset the password with `regulus reset-admin`.
- Everything under `/api/` except `/api/auth/*` needs a login (`401` otherwise). The dashboard files, `/healthz` and `GET /api/database` (one boolean: whether the database answers) are public: they contain no data, and the page shows the login or setup form before anything else.
- Serve the hub over HTTPS outside a trusted network (`tls_cert` and `tls_key`, or a reverse proxy): sessions and passwords travel in the clear otherwise. By default the dashboard answers on `127.0.0.1:8080` only, and the hub logs a warning at start when it serves plain HTTP on any other address (see [Reaching the dashboard](installation.md#reaching-the-dashboard)).
- **Behind a reverse proxy, tell the hub which one** with `trusted_proxies` (a list of addresses or CIDR blocks, in the YAML file, or `REGULUS_TRUSTED_PROXIES` comma separated), for example `["127.0.0.1"]` when the proxy runs on the same machine. Only when the connection comes from one of those addresses does the hub use `X-Forwarded-For` (the rightmost entry that is not itself a trusted proxy; the entries to its left are written by the client and are never used) and `X-Forwarded-Proto` (to mark the cookie `Secure`). That address is what the failed-login limit, the audit log (`remote`) and the session list record. From any other peer both headers are ignored, so a client cannot pick its own address or turn the `Secure` flag on or off. Empty (the default) trusts no header. The proxy must **replace or append to** `X-Forwarded-For`, not pass the client's value through unchanged: nginx `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`, Caddy and Traefik do this by default. It is not in the console settings list because it is a list; edit the file and restart the hub.

Endpoints: `GET /api/auth/me`, `POST /api/auth/setup`, `POST /api/auth/login`, `POST /api/auth/logout`, `POST /api/auth/reset`.

**Users, sessions and audit.** Admins manage accounts in the dashboard (**Users**) or through the API: `GET`/`POST /api/users`, `PATCH`/`DELETE /api/users/{username}`. What each user may do depends on the permissions of their role (`403` when missing). The last enabled admin can never be demoted, disabled or deleted. Disabling or deleting an account ends its sessions at once, and a disabled account gets the same "invalid username or password" answer as a wrong password. Every user can change their own password (`POST /api/account/password`, which ends their other sessions and counts wrong current passwords toward the rate limit) and list or end their own sessions (`GET /api/account/sessions`, `DELETE /api/account/sessions/{id}`; each session records the address and browser it was created from). Account events (setup, logins and failed logins, user changes, password changes, ended sessions) go to an audit log in the database, kept 90 days (events that anyone can cause without a login, failed logins and invalid enrollment tokens, have a budget of their own: the newest 5,000), readable with the `audit.read` permission at `GET /api/audit?limit=` and in the **Users** page (an entry has the English `detail` and, when the place that wrote it has one, a `code` with `args` that the dashboard translates, #368); it never stores passwords or tokens.

**Roles and permissions.** Every endpoint that changes or reveals something checks a named permission, not a role name: `servers.read` (see the servers and their metrics), `servers.manage` (enrollment tokens, rename, revoke), `layout.edit` (arrange the dashboard), `users.manage` (accounts, resets, two-factor policy), `roles.manage` (the roles below), `audit.read` and `core.update` (see and steer the [updates](updates.md)). The built-in roles live in the code: `admin` has every permission, including the ones later versions add; `operator` has `servers.read`, `servers.manage` and `layout.edit`; `viewer` has `servers.read` and `layout.edit`. Anyone with `roles.manage` can make **custom roles** per installation in **Users → Roles** (`GET`/`POST /api/roles`, `PATCH`/`DELETE /api/roles/{name}`, audited): pick a name (lowercase letters, digits, `-` and `_`) and tick permissions. A role in use cannot be deleted, and the built-in ones cannot be changed. Nobody can hand out more than they hold: a role or an account can only be given permissions its author has, and an account can only be changed, disabled, deleted or reset by someone whose permissions cover all of that account's. Changes to a role apply at the next request, with no new login. The signed-in user's permissions are in `GET /api/auth/me`. The OS-level privileges of the services are a separate matter (see the [design decisions](decisions.md#updates) and #46).

**Step-up re-authentication (#279).** A session cookie is all an attacker needs to act as its user, for 7 days. So the actions that would turn a stolen session into lasting control, or install software as root, ask again for the password, and for a code (app or recovery code) when the user has two-factor on. The proof is kept **on the session** (`sessions.reauth_at`) for **5 minutes**; a login counts as one, so right after signing in nothing is asked. Without a recent proof these requests answer `403` with `code: reauth_required`; the dashboard then shows a dialog for the password (and the code), sends it to `POST /api/account/reauth` (`{password, code}` → `{reauth_until}`) and repeats the request. Wrong passwords and codes count toward the same limit as the other checks of a logged-in user (10 per 15 minutes per account), are audited as `password_change_failed` with the detail `re-authentication`, and a success as `reauthenticated`. The proof belongs to one session: another browser of the same user is asked on its own. The check comes after the permission check, so a user without the permission is refused, not asked. The actions and why:

| Action | Endpoint | Why |
|---|---|---|
| Create, change (role, enable/disable) or delete an account | `POST /api/users`, `PATCH`/`DELETE /api/users/{username}` | a new admin, or a promotion, outlives the stolen session |
| Make a password reset link, remove a user's two-factor | `POST /api/users/{username}/reset`, `DELETE /api/users/{username}/two-factor` | takes over another account |
| Change who must use two-factor | `PUT /api/settings/security` | weakens every account |
| Create, change or delete a role | `POST /api/roles`, `PATCH`/`DELETE /api/roles/{name}` | widens what accounts may do |
| Turn the agent listener on, make an enrollment token | `PUT /api/agents/listener`, `POST /api/enrollment-tokens` | a machine of the attacker's enrolled as a trusted agent |
| Revoke an agent | `DELETE /api/agents/{id}` | takes a server out of management; it must enroll again |
| Change the update settings, start a rollout, apply an update | `PUT /api/updates/settings`, `POST /api/updates/rollout`, `POST /api/updates/apply` | software installed as root on the hub or on every server |

Not covered, on purpose: reading anything, renaming a server, cancelling a token, checking for or downloading an update (it is verified and installed only by the actions above), stopping a rollout, the layout, and the own account (changing the password and turning two-factor off already ask for the password and the code). Later actions of the same kind (opening a listener for Regulus Access, promoting a hub, #105) are meant to use the same check.

**Two-factor authentication.** Any user can add a second step to the sign-in from **Account → Two-factor authentication**: after confirming the password the dashboard shows a QR code (and the key, to type by hand) for any TOTP authenticator app (RFC 6238: Google Authenticator, Aegis, 1Password, Bitwarden…). Two-factor is on only after the user enters a valid code from the app, and then ten **recovery codes** are shown once (stored only as hashes; each works once instead of an app code; renewable, which voids the old ones). Afterwards a correct password does not create a session: the hub answers with a short-lived pending login (5 minutes, 5 tries, not a session) and the session starts only after a valid code. Codes are accepted within one 30-second step either side of the clock, and a code works once. Wrong codes count toward the failed-login limit above, and the password step does not reset it. Using a recovery code is audited, logged as a warning and shown to the user at sign-in with the number left. Turning it off, or making new recovery codes, needs the password and a code. TOTP secrets are stored encrypted (AES-256-GCM) with a key derived from `secret.key` in the data directory (created at the first start, readable by the owner only): a copy of the database alone does not reveal them, so back both up. In **Users → Security** an admin can require two-factor from administrators or from everyone; a user it applies to must set it up before anything else (the API answers `403` with `code: two_factor_setup_required` until then) and cannot turn it off. An admin can remove the second factor of a user who lost the app and the codes (**Reset two-factor**, audited; it ends their sessions). Endpoints: `POST /api/auth/login/two-factor`, `GET /api/account/two-factor`, `POST /api/account/two-factor/{setup,enable,disable,recovery-codes}`, `DELETE /api/users/{username}/two-factor`, `GET`/`PUT /api/settings/security`.

**Lost credentials.** The hub does not need email for recovery.

- *A user forgot the password:* an admin opens **Users**, picks **Reset password** and hands the link to the user (`POST /api/users/{username}/reset`). The link is `http://<hub>/#/reset/<token>`: the token is random, stored only as a hash, works once, expires after one hour and replaces any earlier link of that account; it sits in the URL fragment, so it never reaches server logs. The user opens it, chooses a new password (`POST /api/auth/reset`) and signs in; the admin never sees the password. Making the link ends all sessions of the account, and so does using it. Disabled accounts cannot be reset. **Nobody can make a link for their own account** (`403`): an admin who forgot their password asks another admin or uses `reset-admin` on the machine, and one who is logged in changes it from **Account**, which asks for the current password, so a stolen session cannot turn into a new password. Wrong tokens count toward the same limit as failed logins (10 per 15 minutes per address), and every token that is unknown, expired or used gets the same answer.
- *No browser can reach the server on the first run:* on the machine that runs the hub, as the user that owns the data directory, run `sudo -u regulus regulus hub create-admin --config /etc/regulus/config.yaml [--user NAME]` (#369). It asks for the password twice without echo, so it never shows up in the shell history (`--password-stdin` reads one line from standard input for scripts; the password is never a flag). It follows the rules of `reset-admin`: no setup token (access to the data directory is the proof), the hub may keep running, it never migrates the database (the hub must have started once), the account has to pass the same checks as the dashboard's setup, and it **refuses when any account exists** (`reset-admin` is for that case). The event is recorded in the audit log as `console`. The console's first-run screen points to the command. Not verified on a real system with a terminal and the package install.
- *The admin is locked out:* on the machine that runs the hub, as the user that owns the data directory, run `sudo -u regulus regulus hub reset-admin --config /etc/regulus/config.yaml` (with the package install; otherwise pass the same `--config` or `--data-dir` as the hub, and `--user NAME` if there are several admins). It prints a one-time reset link like the one above for that admin, enables the account if it was disabled and ends its sessions; the hub can keep running. Whoever can write to the data directory owns the hub anyway, so that access is the proof of ownership. The password is chosen in the browser, so it never shows up in the terminal or the shell history. The command is recorded in the audit log as `console`. It never changes the database schema: right after a package upgrade, before the hub has restarted and migrated, it refuses and asks you to restart the hub first (`systemctl restart regulus`).
- *The admin lost the authenticator app too:* `reset-admin` also removes the admin's two-factor authentication (console access is the proof of ownership), so the new password is enough to sign in; set it up again from **Account**. For other users, an admin uses **Reset two-factor**; nobody can reset their own (`403`): a logged-in user turns it off from **Account** with the password and a code, so a stolen session cannot strip the second factor. Passkeys will be cleared by a reset when that feature exists.
