# Design decisions

The choices behind Regulus that the code alone does not explain: what was decided, why, and what is still open. The README says *how* things work; this file says *why they are that way*. When a decision changes, update this file in the same pull request.

## Tech stack: Go and React

Hub and agent are written in **Go**, the dashboard in **React with TypeScript**. The alternatives considered were: hub in C# with the agent in Go, everything in C#, Rust, and Node.js.

Go was chosen because:

- the agent must stay light even on a small VPS (512 MB of RAM);
- it builds a **single executable with no runtime** to install, so one package serves both roles;
- the agent opens an **outbound** connection to the hub, and Go's gRPC support handles that well;
- plugins run as **separate processes speaking gRPC**, so they are not tied to Go: a plugin can be written in C# or any other language with gRPC.

Any memory or size figures quoted while choosing were orders of magnitude, not measurements.

## License: Apache-2.0

Apache-2.0 was preferred to AGPL-3.0. A permissive license makes it easier for others to write and distribute plugins (#23); AGPL would protect the project more but would discourage third-party plugins. Changing the license after outside contributions is hard, so this choice is tied to the plugin strategy.

## Platforms

Ubuntu Server comes first because it is the system used for the first real tests. The order is:

1. Ubuntu LTS 22.04, 24.04 and 26.04, amd64 and arm64, `.deb` package (26.04 amd64 is the one tested on a real machine so far, #81; whether 22.04 stays is open in #89);
2. Debian, with the same `.deb`;
3. RHEL-like distributions, `.rpm` package.

Other distributions with systemd can use the `tar.gz` archive. An apt repository or PPA for Ubuntu is postponed.

What runs where (#230; the table is in [Remote agents](remote-agents.md#supported-platforms)):

- **Releases are Linux amd64 and arm64 only, on systemd.** Updates from the dashboard need systemd: the root helper is started by path units. Linux without systemd runs the agent from the `tar.gz` but gets no updates; another OS is not built.
- **An agent that cannot read something says so** instead of sending zeros: every `MetricsReport` names its collector (`linux` or `basic`, fields 9 and 10 with `unavailable`) and the parts it could not read. Added to protocol 1 without raising `protocol.Version`: an older hub ignores the fields, an older agent sends none and looks as before. The hub keeps them in the stored report (an empty list costs nothing), so a metrics point says what its zeros mean. The basic collector is still chosen once at start, by reading `/proc/stat`; the Linux collector reports per report what it could not read.
- **No cgroup limits (at first; #325 and #355 added them).** CPU, load and memory come from `/proc`, so in a container they are the host's unless LXCFS virtualizes `/proc`; the cgroup now replaces memory, swap, CPU usage and the CPU count, and only the load average stays the host's. The agent reports the container it detects (`SystemInfo.container`, field 8) and the dashboard says which figures may be the host's. Reading the cgroup limits of memory and the CPU quota was left for a follow-up, which is the section "Containers: the agent reads its cgroup limits (#325)" below.
- **Network filesystems and overlay are not disks.** nfs, cifs and the like belong to the server that exports them (which reports them with its own agent) and are the mounts most likely to hang; overlay is a container's view of the host's disk. A container therefore shows "No disks reported", which is not the same as "not available".

## Roadmap: phases and milestones

The README describes four **phases**; the work is tracked in six **milestones**, M1 to M6. Issue titles still carry the phase they were first written for (`[Phase 1]`, …), so a title and a milestone can disagree: the milestone is what counts.

| Milestone | Content | Phase |
|---|---|---|
| M1 | Foundations: skeleton, hub core, agent-hub contract, CI, release workflow | 1 |
| M2 | Hub with built-in agent and dashboard: authentication, users, widgets, Ubuntu packaging | 1 |
| M3 | Remote agents: enrollment, multi-server dashboard, agent installer | 2 |
| M4 | Separate hub and agent, protocol versioning | 3 |
| M5 | Update system | 3 |
| M6 | Plugins | 4 |

Some issues were moved after they were written, so their title names an earlier phase:

- **Two-factor authentication (#49) in M3**: it should exist before one dashboard manages several servers.
- **Passkeys (#50) in M4**: WebAuthn needs HTTPS and a public domain (`public_url`), which come with the separate hub.
- **User management (#48) and credential reset (#51) in M2**: without a reset, an administrator who is locked out cannot get back in.
- **Roles (#61) and the terminal console (#52) in M3**; **privileged actions (#60) and server inventory (#62) in M4**; **AI Support (#63) in M6**.

Third-party plugins (#23) have no milestone: they come after the plugin system is stable.

## Releases and channels

Three channels: **stable** (`v0.3.0`), **beta** (`v0.3.0-beta.N`; `-rc.N` counts as beta) and **alpha** (`v0.3.0-alpha.N`; any other pre-release counts as alpha, so an unknown kind never reaches a more cautious channel). Each channel also offers the more stable ones: alpha sees everything, beta sees betas and releases, stable only releases. A hub starts on the channel of the version it runs.

Releases are published from the Actions tab (**Publish release**), not by typing tags, so that versions always follow SemVer order: a version goes through its alphas, then its betas, then the release, and no alpha comes after a beta of the same version. The workflow refuses a commit on which CI has not passed. It must start the release workflow **on the tag**, because the hub only trusts a signature made by `release.yml@refs/tags/<tag>`.

## Updates

**Goal: install once.** After the first installation, an administrator should never have to install anything by hand from a terminal: hub, agents and (later) plugins are updated from the dashboard. Today this holds for hub and agents. Still missing: plugin updates (#19, #20) and two exceptions [updates](updates.md) lists (an agent installed before the update feature, and a release that changes the systemd units or the configuration file, #254).

**One piece at a time.** It must be possible to update an agent, the hub or a plugin on its own. Versions may require others: agents and hub negotiate the protocol and the hub accepts agents of its own release series and the previous one (#17, [remote agents](remote-agents.md), "Versions"); plugins declare the core versions they need with `requires` (#19, [plugins](plugins/README.md)).

**Who decides.** The administrator chooses the mode in the dashboard: `manual` (tell me), `download` (download and verify, then wait for my approval) or `automatic` (install inside a maintenance window). The default for a new installation is **`download`**: nothing is installed without an administrator's approval.

**How the privileged step works.** The hub runs as the unprivileged user `regulus`. Installing a new binary is done by a root helper started by a systemd path unit (`regulus-update.path`, `regulus-agent-update.path`), which the installer enables unless `--no-self-update` is given. The helper acts only on a request naming a version, and checks everything again itself. Releases are signed with **Sigstore keyless** (GitHub Actions identity). An earlier design used a `sudoers.d` rule and minisign or cosign keys and disabled self-update for package installations; that design was replaced by the current one. Whether `sudoers.d` or a root helper is better for the other privileged actions (services, packages, Docker) is still open in #60.

## The repository moved (audit issue #231)

The repository moved from `CodexCircle/Regulus` to `Stellatinus/Regulus`. Releases are signed with the identity of the release workflow of the repository that ran it, and the hub, the agents and the root helper accept only `update.Repository` (`internal/update/signature.go`), so the move needed a change in code, not only in links:

- **One name in Go code:** `update.Repository` feeds the release feed (`hub.ReleaseRepo`) and the signature identity. `packaging/install.sh` (`REPO`) and the documents repeat it; `TestNoStaleRepositoryName` fails when the old address is left in any text file, and `TestInstallerUsesTheReleaseRepository` checks the installer.
- **`v0.2.0-alpha.1` is signed by the new repository** (checked in its Sigstore certificate), but the binary of that release still trusts the old identity. A server running it **cannot update itself** to any later release: reinstall with `install.sh` from the new release (see [Updates](updates.md)). Releases up to `v0.1.0-alpha.1` were signed by the old repository.
- **Why not trust both names:** a name that can be registered again by someone else would let a stranger sign releases that every installed hub accepts. Only the current repository is trusted.
- **The Go module path stays `github.com/CodexCircle/Regulus`** on purpose: it is an import path, nobody downloads the module from it, and renaming it touches every import and the generated code (regenerating needs `make proto`). It can be renamed later in one mechanical pull request; until then it is the only place where the old name remains, together with the product name "CodexCircle Server Manager", which the maintainer will decide on separately (see the naming plan in the [glossary](glossary.md)).

## Updates: the rollback restores the SQLite database (audit issue #205)

A rollback that put back only the program failed in the one case it exists for: the new version migrated the database and then did not come up, and the previous version refuses a database with a migration it does not know (`storage/migrate.go`). For SQLite the root helper now takes a consistent copy before the swap (`storage.SnapshotSQLite`), refuses the update if it cannot, and puts the copy back on a rollback only when the schema moved (`storage.RestoreSQLite`, after stopping the service and removing the write-ahead log, which belongs to the file being replaced). It accepts losing what the new version saved after the copy, and says so in the result. For PostgreSQL it does nothing and the documents tell the administrator to back up first: a server cannot be copied from the helper, and the real answer there is a rule that a release's migrations are ones the previous release can live with, which is not written yet (the strict "unknown migration" check stays).

## Updates: a schema range and expand-only migrations (audit issue #247)

The strict check ("refuse every migration this binary does not know") made every rollback on PostgreSQL end with a program that cannot start, because the helper cannot copy a database server. Each migration now records `reader_min`, the lowest migration version a binary must know to work on a database that has it; it defaults to the migration's own version (strict, the old behaviour) and an expand-only migration lowers it with `-- regulus:reader-min N`. A binary refuses a database only when an unknown migration needs more than it knows. The rule is that a release's migrations expand and a later release contracts; a test fails for a destructive statement in a migration newer than the baseline unless the migration is strict and listed. `reader_min` is added to `schema_migrations` by the runner, not by a numbered migration, because the runner has to read it before it can judge any migration. **Not done:** the helper does not refuse to update a PostgreSQL hub without a confirmed backup (the Updates page says what a rollback does not restore, and the backup is the administrator's call); the previous release's program is not run against the new schema in CI, only its migrations; the lowest supported schema is not a separate check, since a binary migrates an older database forward.

## Disks: an identity that belongs to the drive (#148)

A disk has no MAC address, so the identity key is the best identifier the drive reports: WWN, EUI-64 or NGUID, then model plus serial; the kind is stored with the key. Device names, UUIDs and the hostname are never used. **The agent sends raw identifiers and the hub decides the key** (`internal/diskid`), so a better rule needs no new agent. A disk with no reliable identifier (no serial, a filler serial, a hypervisor's disk without a WWN, a USB enclosure without one) is *not identifiable* and is tracked per server and slot, rather than given a key that could join two different disks; duplicates within one report are flagged, and both lose their key. The field is added to `MetricsReport` in protocol 1 with its own `disk_identity_version`, without a protocol bump. A new permission, `inventory.read`, guards the serial numbers (`admin` and `operator`; not `viewer`); the operator has it because the role works with the servers, which is open to change. The migration only adds tables and declares `reader-min` (#247). **Not decided or not done:** cross-server duplicates (two servers reporting one disk at once are moves back and forth), the dashboard (there is no inventory page, #62), the event log (#150), and whether a hypervisor disk with an explicit serial should be identifiable. Not verified on a real disk.

## The example plugin, and what #22 could and could not deliver

The issue asks for an example with an agent side and a widget, and a guide that covers the gRPC API and the widget. The plugin contract has only `Describe` and `Health`, and the widget loader (#21) and the host side of plugin features are not designed. So the example keeps its own state in its data directory, is healthy while that directory is writable and ships `ui/widgets.js` in the shape #21 proposes, marked provisional and loaded by nothing; the guide says so instead of describing an API that does not exist. `scripts/package-plugin.sh` makes a `<id>_<version>_<os>_<arch>.tar.gz` with a checksum, unpacked into the plugins directory; the name and layout are provisional until #20. The `.gitignore` now ignores `plugins/*/bin/`, which the guide already claimed it did.

## Load measurements over real connections (#370)

`TestHubUnderRealLoad` runs the real binary as a separate hub process, so its CPU and memory are its own, with real mTLS agents, a real WebSocket per dashboard and a database write per user per second, on SQLite and PostgreSQL. The first run (docs/development.md) found nothing to fix at 200 agents and 20 dashboards: a few percent of one CPU, millisecond fan-out. It is loopback on one machine, so network latency and several machines stay unmeasured, and the browser measurement is Chromium's own metrics, not the React Profiler. No per-connection memory is claimed: the hub's start-up peak hides it.

## One hub per data directory, and reset-admin does not migrate (audit issue #217)

Nothing stopped a second hub on the same data directory: it removed the first one's status socket, raced it on the SQLite migrations (the migration lock existed only on PostgreSQL) and on the creation of `secret.key`, and ran a second set of timers (automatic rollout, update checks). Choices:

- **A lock on the data directory, not on the database file.** `hub.New` takes an exclusive, non-blocking `flock` on `<data_dir>/hub.lock` before it touches anything in the directory (`internal/hub/datadir_lock_unix.go`); a second hub fails at once with `ErrAlreadyRunning`, the path of the lock file and the process id written in it. The kernel drops the lock when the process ends, however it ends, so a killed hub leaves nothing to clean up, and the file is never removed (removing a lock file lets two processes lock two different files). This also makes the removal of a leftover `regulus.sock` safe. On systems without `flock` (not released) there is no lock. A lock in the database (a row with a lease) was rejected: it needs a lease length, a clock and a takeover rule, and the data directory holds more than the database (the CA key, the secret, the socket).
- **PostgreSQL: a session advisory lock "active hub"**, named after the schema (`hashtext('regulus-active-hub:' || current_schema())`), taken by `storage.OpenHub` **before** the migrations, on a connection the hub keeps. A second hub on the same database (from another machine) fails at once with `ErrHubActive` and does not migrate, which matters when it is a newer version. The lock lives as long as that one session, so the database watcher (every 15 s, `hub/dbwatch.go`) also checks that the hub still holds it (`HubDB.EnsureActive`, #344). If PostgreSQL ended the session (server restart, `pg_terminate_backend`, a long network cut) the hub takes the lock again on a new session and logs a warning; if the old session is only stale on the server (a cut network PostgreSQL has not noticed), the hub ends its own stale backend first, and only when that backend holds this very lock. If another hub already holds the lock, two hubs are running on one database: this one logs an error, stops the timers that must run in one place (update checks and automatic rollouts) and shows the problem in `regulus status` and the console. It keeps checking the lock at every watch: when the other hub is stopped and the lock is free, this hub takes it, clears the problem, logs a warning and starts the timers again, **without a restart and without the administrator's approval** (#356; the lock is the only authority, because a hub that holds it is by definition the only one running on that database; with a redundant hub the term of #108 will decide, and this check is where that rule goes). It does not stop serving: ending the process would hide the situation and a service manager would only restart it into the same conflict. Tested against a real PostgreSQL with `pg_terminate_backend`. A hub killed a moment ago may leave its session open briefly; the service manager retries (`Restart=on-failure`, 5 s). The design of a second, standby hub (epic #103) builds on this rule; it does not exist yet.
- **`reset-admin` never migrates**: it opens the database with `storage.OpenExisting`, which creates no file and refuses a schema that is not exactly the binary's: a newer one, or an older one (after a package upgrade, before the service restart), with the advice to restart the hub first. Migrating from a tool beside a running hub would change the schema under the old hub. It does not take the data-directory lock: it is meant to run while the hub runs.
- **`secret.key` is written to a temporary file, synced, then hard-linked to its name**: a link is made in one step and never replaces a file, so a reader sees the whole key or no file, and a crash leaves at most a stray temporary file instead of an empty `secret.key`.

## SQLite: one writer and a read pool, and no audit write under a lock (audit issue #219)

The hub used one SQLite connection for everything although the database is in WAL mode, which lets readers run beside a writer; every authenticated request checked its session on that connection, behind any write or slow read. Choices:

- **`storage.OpenHub` returns two pools** (`HubDB.Write`, `HubDB.Read`). Write is the one connection as before, now with `_txlock=immediate`, so a write transaction takes the write lock at `BEGIN` instead of upgrading a read lock later. Read is a pool of 4 (`DefaultReadConns`) with `query_only(1)`, so a write sent to it by mistake fails instead of competing with the writer. On PostgreSQL, Read is the write pool (it already has 10 connections). `storage.Open` (tests, tools) keeps one pool.
- **Who reads where.** Only reads that need not see a transaction of their own use Read: the session check and the role lookups (`auth`), the lists of users, sessions and audit events, `fleet.Authorize` (the check of a connecting agent), `fleet.Agents`, the pending enrollment tokens, and the dashboard layout; and, since #345, the update settings and state (`update.Options.ReadDB`), the two-factor enrollment and recovery-code count and the security policy (`auth`), and the saved agent listener. Each was reviewed: they are single reads of committed rows (every earlier write is its own committed statement, and a committed row is visible to the next read in WAL mode), none runs inside a transaction of its own, and none decides a write by itself (the check that matters, such as a TOTP step or a recovery code, is still one `UPDATE` on Write). `tryPending` stays on Write: it is an `UPDATE ... RETURNING`. Everything else stays on Write; moving more is safe only for a read that is not followed, in the same flow, by a write that depends on it.
- **The session check writes only when needed:** `last_used_at` is updated when it is a minute old or more, decided in Go from the row just read, not by an `UPDATE ... WHERE` on every request, which needed the writer each time.
- **The audit write of a rollout start is outside `rollout.mu`.** The run is registered and counted (`wg.Add`) under the lock, the event is written after it is released, and a stop writes its own event after the run has ended, so the events stay in order and the status endpoint never waits for the database.
- **Nested use is still caught:** `make test-one-connection` (also a CI step) runs the hub tests with `REGULUS_TEST_ONE_CONNECTION=1`, which gives the hub no read pool, so code that queries while a transaction or a result set of its own holds the one connection hangs and the test times out. The other packages' tests already use one connection (`storagetest.Open`).
- **Measured, not on a real machine:** `BenchmarkReadLatencyDuringAuditWrites` (`internal/hub/readpool_test.go`): 200 enrolled agents, 20 dashboards reading at once (session check and the server list) while audit events are written in transactions that each hold the writer for 20 ms. In the cloud container (4 CPUs): median 4.6 ms and 99th percentile 39 ms with the read pool, against 60 ms and 233 ms with one connection. The remaining tail is the 20 reads sharing 4 connections and the CPU, not the writer: `TestReadsAndAgentsDoNotWaitForTheWriter` holds a write transaction open and checks that the dashboard reads and a remote agent's connection still complete.

## Agent presence is written off the handshake path (audit issue #218)

`register` wrote `last_seen_at` synchronously before the Welcome, with no timeout, so a busy SQLite connection or a PostgreSQL outage held every new agent; the value was written only at connect and disconnect, so a hub that crashed left offline agents with a wrong "last seen"; and the disconnect write could run after the database was closed. Now a **presence writer** (`internal/hub/seen.go`) owns these writes: the handshake only queues them (never waits), writes are coalesced per agent and kind (the latest wins), each has a 5-second timeout, a failure is logged once until writes work again and the record is dropped (the next flush writes it again). Every **minute** the connected agents are recorded as seen, so `last_seen_at` is at most a minute old after an unclean stop, at the cost of one `UPDATE` per connected agent per minute (200 agents: about 3 a second, small for both backends). `Hub.Close` records the connected agents a last time and stops the writer **before** the database closes; what is queued later is dropped. The certificate end of #245 (`CertificateSeen`), the other write of a connection, goes through the same writer. `Authorize` stays on the path (an agent must be checked before it is admitted) but is bounded to 10 seconds; a refused agent retries. Rejected: writing on every heartbeat (a write per agent every few seconds for no gain the minute flush does not give) and a write-behind cache read by the API (the API reads the registry from the database, and connected agents are shown from memory anyway).

## Enrollment tokens: list, cancel, and one transaction (audit issue #202)

A token could not be listed or cancelled, and `Enroll` deleted it before signing the certificate and inserting the agent, so a malformed request or a database failure burned it. Now `Enroll` reads the token, signs, and then deletes the token and inserts the agent in one transaction; the delete must affect exactly one row, so two requests with the same token cannot both enroll (the loser signed a certificate that nobody receives). A token is named in the API by the first 16 hex digits of its hash: no migration (a rollback of the hub after a migration is the hard case, see the update decisions), and the prefix cannot be turned back into the token. The lifetime is an optional `ttl` in the creation request (1 minute to 7 days, default one hour), not a hub setting, because it depends on how the admin will hand the token out. Not done: a lifetime field in the dashboard form (the API has it).
## Browser security headers (audit issue #201)

Every response of the hub's HTTP port carries a content security policy that allows only the hub's own origin (plus `data:` images, for the QR code of the two-factor setup), and forbids framing, plugins and a changed `<base>`; also `X-Frame-Options: DENY`, `nosniff` and `Referrer-Policy: no-referrer`. HSTS (one year, no `includeSubDomains`, no `preload`: those can lock a whole domain out and are the operator's call) is sent only when the request came over TLS or the proxy says so in `X-Forwarded-Proto`; a browser ignores HSTS over plain HTTP, so believing that header from anyone is harmless there. Not done: the `__Host-` cookie prefix. It needs `Secure`, so the cookie name would depend on whether the request came over HTTPS (the hub also serves plain HTTP) and every reader would have to try both; `HttpOnly`, `SameSite=Lax` and `Secure` behind HTTPS already cover what it adds for a cookie that is set only by the hub. The CSP was checked in Chromium with the built dashboard (login, live stream, the two-factor QR code): no violation. It was not tried in Firefox or Safari, where `connect-src 'self'` for the WebSocket should behave the same (Safari before 15.4 did not match `ws:` with `'self'`).

## Dashboard live data: a store with keys per agent (audit issue #224)

The live data of the widgets used to be one React context `{state, connection, now}` rebuilt at every stream message, and each report copied the whole series (up to 3600 points) of its agent; every widget of every agent was drawn again. Now `LiveProvider` fills a `LiveStore` (`dashboard/src/live.ts`) kept outside React. Components read it with `useSyncExternalStore` and subscribe to keys: the list of agents (which changes only when agents come, go or are renamed), one agent, and the status (connection, readiness, the clock). A report of agent A therefore wakes only the widgets that show A. Each agent's reports are in a ring buffer (`PointRing`): appending is constant time, and the 10-minute window a chart draws is cut with a binary search and cached until the next report, so the work per message does not grow with the length of the series; widgets memoise what they derive from that window (`derive` in `BaseWidgets.tsx`). The history is loaded only for agents a widget shows (`useLiveAgent` calls `store.watch`), and only the newest 600 reports (`?limit=`, added to `GET /api/agents/{id}/metrics` for this): enough for 10 minutes at the shortest metrics interval. An agent nobody shows still gets its reports from the stream; after a reconnection its series has a gap, so it is loaded in full when a widget shows it again. Checked by tests (50 agents × 3600 points: a report of one agent draws one widget again, and a timing test compares the cost per message with 36 and 3600 points); not measured in a real browser.

## Dashboard: checked JSON, a root error boundary and reconnection with jitter (audit issue #229)

`request()` in `dashboard/src/api.ts` throws an `ApiError` with code `invalid_response` (and the HTTP status) when a 2xx answer is not JSON: by its `Content-Type`, or because it does not parse. A proxy error page or a captive portal answering 200 used to surface as a bare `SyntaxError`. The live data is checked by small guards (`dashboard/src/shapes.ts`) rather than a schema library: an agent needs an id, a report needs a valid time and every number the widgets read, missing or `null` disk and network lists become empty, and what fails is dropped (a stream event, a report of the history, an agent of a snapshot). The guards check what the widgets read, not the whole API. `RootBoundary` around the app (in `main.tsx`) replaces a white page with a message and a reload button; widgets keep their own boundary. The stream reconnects after a delay that doubles up to 15 s with up to half of it left out at random, so dashboards cut off together do not come back together; the delay returns to the first one only after a connection stayed open 5 s (`STABLE_MS`), so a hub that accepts and closes at once is not hammered, and after the hub's `1008 "too slow"` close the first wait is at least 5 s. Checked by tests with a fake socket and fake timers, not on a real network.

## Sign-in errors in the user's language (audit issue #311)

The sign-in, code and setup forms (`useSubmit` in `dashboard/src/AuthGate.tsx`) map the status of the answer to catalog keys (`auth.error.*`) instead of showing the hub's English text: 401 is wrong credentials, or at the code step a wrong code or an expired sign-in; 403 and 409 on setup are a wrong token and a setup already done; 429 says how many minutes to wait, rounded up from `Retry-After` (which `ApiError.retryAfter` now carries, seconds or an HTTP date); 503 makes the form try again by itself after `Retry-After` seconds (5 when absent), at most three times, with a note meanwhile. The hub's text stays only as the fallback (a 400 on input the hub refused, such as a password that is too short). To tell a wrong code from an expired sign-in without reading English, the 401 of `/api/auth/login/two-factor` now carries `code: invalid_code` or `code: login_expired`; a client that ignores the code sees no change. Checked by tests with a fake `fetch` and fake timers, not in a real browser.

## Metrics history: buckets on the hub, generic errors in the catalog (#320)

`GET /api/agents/{id}/metrics` takes `step`, a Go duration from `1s` to `1h`, and averages the reports into buckets of that length (`internal/hub/downsample.go`), so a chart of a long window downloads one point per bucket instead of every report. A duration was chosen over `points=N` because buckets aligned to multiples of `step` since the Unix epoch do not move between requests: a client that polls with `since` gets the same buckets, with the newest one possibly still filling. A bucket's point is stamped with its newest report's time (so `since` keeps working), averages CPU, load, memory and swap in use and the network rates (null rates left out), and keeps the newest report's totals, uptime, disks and counters. The order is since, step, limit. The dashboard uses it since #330: each CPU, Memory and Network chart has a range choice, 10 minutes (the live stream, one point per report) or 1 hour (`?step=8s`, about 450 buckets, `dashboard/src/history.ts`). The two are never mixed: a live report is one sample and a bucket is a mean, so the one-hour chart is loaded again once per bucket (at most every 10 s) and ignores the stream. The hub keeps one hour, so that is the longest range.

The hub's own error texts are English, so the main refusals of the user, role, account and two-factor endpoints carry a `code` (`internal/auth/http.go`, `errorCodes`: `user_exists`, `last_admin`, `forbidden`, `wrong_password`, `two_factor_off`, …) next to the English `error`, which stays for scripts. The dashboard turns a known code into a catalog text, `hub.error.<code>`, in English and Italian, when the request fails (`hubErrorKey` in `api.ts`, the mechanism of #320); an unknown code, or none, shows the hub's text as before. An answer that is refused for lack of input (400) keeps the hub's English text.

The texts `request()` writes itself (an answer without an explanation, an answer that is not JSON, no answer at all) are now catalog keys (`request.*` in the core area): the `ApiError` message is written in the page's language when the error is made and keeps the key and parameters (`messageKey`, `messageParams`), so `apiErrorText(t, err)` can write it again in another language. A failed `fetch` (network down, hub stopped) becomes an `ApiError` with status 0 and code `network_error` instead of a bare `TypeError`; an abort is passed through unchanged. The hub's own explanations are still shown as the hub wrote them (in English) outside the sign-in forms (#311).

## Resetting one's own credentials is refused (audit issue #203)

`CreateReset` and `ResetTwoFactor` refuse the caller's own account (`403`). Both used `mayManage`, which lets a user manage themselves, so a stolen admin session could make its own reset link or strip its own second factor without the password the normal flows ask for. We chose to refuse rather than to ask for password and code in these paths, because the normal flows already exist (`ChangePassword`, `DisableTwoFactor`), the dashboard already disables these buttons for oneself, and an admin who lost everything has `regulus hub reset-admin` on the machine (it does not go through these two methods). A stolen session could still create another admin; step-up re-authentication (#279, below) now asks for the password again for that and the other sensitive actions.

## Step-up re-authentication for sensitive actions (audit issue #279)

Follow-up of #203: a stolen admin session could still create another admin, hand out permissions, enroll a machine of its own or install an update. Those actions (the table in [Authentication](authentication.md)) now need a proof of the password, and of the second factor when on, no older than **5 minutes**. Choices:

- **A recent proof kept on the session, not the password in every request.** One dialog covers a short series of changes (create a user, then set the role), and the API of each action stays as it was. The proof is a column of `sessions` (`reauth_at`, migration 0014), not memory, so it survives a restart and will be shared by redundant hubs (#103); a session from before the migration has none and is asked once.
- **A login counts as a proof**: the person just typed the password and the code. So an admin who signs in and acts at once is not asked twice. The cost: a cookie stolen within 5 minutes of a login works without asking, which the window accepts.
- **The answer is `403` with `code: reauth_required`**, not `401`: `401` means "no session" and sends the dashboard to the login page. The dashboard handles the code in one place (the API client) and repeats the request once after the dialog, so no page needed its own handling.
- **Checked after the permission**, so a viewer is refused, not asked for a password.
- **A recovery code is accepted** instead of the app code, like the other checks of a logged-in user, and is used up.
- **Which actions:** the ones that give a lasting way in, change what others may do, or install software as root; also revoking an agent, which is destructive and was named in the issue. Renaming, cancelling a token, checking and downloading updates and stopping a rollout are not: they give nothing lasting. The own account already asks (password change, two-factor off).
- **Not verified in a browser.** Go tests cover each endpoint without and with a proof, password and code, a recovery code, the limit; dashboard tests cover the dialog and the retry with a mocked API.

## The client address behind a reverse proxy: `trusted_proxies` (audit issue #196)

`X-Forwarded-For` and `X-Forwarded-Proto` are believed only when the peer of the connection is listed in `trusted_proxies`; the client is the rightmost entry that is not a trusted proxy. The default is an empty list, so a hub with nothing in front of it ignores both headers, which also closes the old hole where any client could mark its own cookie `Secure` or not. The setting is a list, so it is read from the YAML file and `REGULUS_TRUSTED_PROXIES` but is not in the console settings table (`regulus config set` edits scalars). The `Forwarded` header (RFC 7239) is not read. The agent port is not affected: it has no proxy in front (mutual TLS).

## The dashboard listens on loopback by default; HTTPS from the hub (audit issue #197)

`listen` defaults to `127.0.0.1:8080` (built in and in the packaged `config.yaml`); it was `:8080`, every interface, over plain HTTP, so a fresh install exposed the login, the first-admin setup and the enrollment token (with the CA fingerprint) in cleartext to the whole network. We chose loopback over "require an explicit `listen`" because the installer must give a working hub with no question asked (`--yes`, `curl | sh`), and an SSH tunnel is enough for the first admin; the installer and the package print the tunnel command. The hub can now serve HTTPS itself (`tls_cert`, `tls_key`): one pair of PEM files, TLS 1.2 or later, HTTP/1.1 only (the live view is a WebSocket, which browsers open over HTTP/1.1, so HTTP/2 would bring nothing and a second code path), files read again at most once a minute so a renewed certificate needs no restart, a half pair or a key that does not match stops the hub at start. With TLS on, `isHTTPS` is true from the connection itself, so the cookie is `Secure` and HSTS is sent without a proxy. Not done: generating a self-signed certificate (a browser warning on every visit trains people to click through; the tunnel is the better default), ACME, client certificates. The two paths are not in the console settings table (a pair, like `trusted_proxies`).

The hub logs a warning at every start when it serves plain HTTP on an address that is not loopback (the bound address is checked, so `:8080` counts as every interface). It warns also behind a reverse proxy on another machine, because that hop is plain HTTP; the fix is TLS on the hub or a proxy on the same machine.

**Upgrades keep the old exposure, on purpose.** dpkg replaces a configuration file the admin never edited, and the new built-in default applies when `listen` is missing, so an upgrade would have taken a working dashboard off the network silently (including after an update started from that very dashboard). The package's pre-install step therefore adds `REGULUS_LISTEN=:8080`, with a comment, to `/etc/regulus/regulus.env` when the old address was `:8080` or unset and nothing in that file sets it already; it says so on the terminal. An address the admin chose is kept by dpkg anyway. The warning in the log is what pushes such a hub towards TLS. **Not verified on a real machine:** the conffile replacement and the pre-install step during `apt` upgrades from the previous release, a fresh install's printed instructions, and HTTPS in a browser (only Go tests: a self-signed pair served over TLS, reload, refusal of a half pair, the warning).

## The audit log: time retention and a separate budget for failures anyone can cause (audit issue #200)

The audit log was capped at 10,000 rows with a second `DELETE` after every insert, and a failed login or an invalid enrollment token (the agent port is reachable by anyone) counted like a user change, so a few thousand requests from many addresses (the limiters are per address, an IPv6 /64 each) pushed out the history an administrator needs. Now an insert only inserts. `auth.Service.Run`, started by `Hub.Serve`, prunes when the hub starts and every hour: events older than 90 days go, and then the oldest ones beyond a budget per class: the newest 5,000 for `login_failed` and `agent_enroll_failed`, 100,000 for everything else (a backstop only; those events need a login or the machine). We chose separate budgets in the same table over the issue's other option, one row with a count per repeated failure, because it needs no migration, keeps one row per attempt with its address, and gives the same guarantee. The cost: between two prunes a burst is bounded only by the limiters, and the rows of one flood are not merged. The list of unauthenticated events is `auth.unauthenticatedEvents`; a new event that a stranger can cause must be added there (the fleet's `agent_enroll_failed` is spelled in auth and kept equal by a test in `internal/hub`). The pruning queries were run on SQLite and on PostgreSQL 16.

## Agents that are too old: an update-only session (audit issue #212)

Before, an agent more than one release series behind (or speaking a protocol the hub dropped) was refused, and updates travel over that same connection: a server that was off for a few months could only be brought back with a terminal and a new enrollment token. Options weighed, and why:

- **Force every agent to update before the hub** (the hub refuses to update while one is behind): one switched-off machine would freeze the updates of the whole network. Rejected.
- **Widen the window** (accept 3 series instead of 2): only moves the cliff. Rejected.
- **Let the agent fetch the newest release from the internet by itself**: agents need no internet today (they get the release from the hub over mTLS), and many are not allowed to reach it. Rejected.
- **Chosen: an update-only session on a frozen update contract.** The hub admits an *enrolled* agent that is too old with `Welcome.update_only`; in that session only `Hello`, `Welcome`, `Heartbeat`, `Ping`, `ApplyUpdate`, `CommandResult` and `FetchUpdate` are used, and their meaning never changes in any protocol version (`protocol.UpdateContract` stays 1, tested). The update goes straight to the hub's version. An old agent that does not know the field keeps sending metrics; the hub drops them, because their format may have changed. The hub refuses every other command for that agent (`ErrUpdateOnly`).
- **Still refused:** an agent with no certificate (nothing enrolled, nothing to update), and an agent newer than the hub (the hub is the one to update).
- **Not solved by this:** an agent that cannot verify today's signatures (a build that trusts the old repository identity) or that has no update helper: `install.sh` once. Both are said in the documents and the dashboard.
- **Not verified on a real machine:** a real agent of an old release against a new hub. The end-to-end test (#233) checks the refusal of another protocol version over the real listener with a hand-made Hello, not an old binary.

## Versioning: contracts instead of modules (#227)

The maintainer asked whether Regulus should be split into more modules (for example a separate, long-lived communication module) to make downloads smaller and parts last longer. Decision: **one executable, and a list of contracts, each versioned and checked on its own** ([versioning.md](versioning.md)). A separate module would only last longer if its interface never changed, and that is a property of the contract, not of the file; with one file there is one signature and one install path, and the compatibility matrix is the short list of contracts instead of every pair of modules. Plugins are the exception, since they are released separately ([plugins](plugins.md)).

CI now runs `buf breaking` against `main` (`make proto-breaking`), and golden files of protocol 1 messages are decoded by today's code (`internal/protocol/testdata/v1`). The golden files were written by the code of this pull request, while the protocol is still at version 1 and no field has changed number or type since the first release; they freeze that state from now on, they are not bytes captured from an old binary. The agent now checks that the protocol version the hub picks is one it speaks.

## Updates: an interrupted update is settled when the machine starts (audit issue #246)

A power cut between the swap and the confirmation left a new version that nobody had watched; if it did not work, systemd restarted it for ever and the previous version came back only at the next update request. Choices:

- **Two steps, because of systemd ordering.** A unit ordered before `regulus.service` cannot restart or start it (the job would wait for the unit that asks), and a service that has not started cannot be judged. So `regulus-update-recover.service` (before) does only what needs no running service, and `regulus-update-confirm.service` (after) runs the existing `update-apply --recover`, unchanged: the health check after a power cut is the same code path as after a killed helper, not a second implementation.
- **A shell script in front** (`/usr/lib/regulus/update-recover`), because the recovery must not depend on the file it may have to repair. It does one thing without the executable: put the kept copy back when `/usr/bin/regulus` does not answer `version` (an empty file counts as broken, although a shell "runs" it). Everything else stays in Go, where it is tested.
- **Why not always roll back at boot** (simpler, no second step): it would throw away an update that is fine, and with it what the new version saved, each time the power fails during the 90 seconds of the health check.
- **A new version gets two starts of the machine, within an hour.** Without a limit, a version that takes the machine down would do so for ever. Without the hour, a marker left for days by a confirm step that never ran (masked, or broken on a system we did not test) would make the third reboot restore a database that is weeks old. Counting only close starts keeps the first protection without the second risk. A clock that went backwards counts as close.
- **A lock** in the state directory serialises the helpers, now that one can be started at boot while a request arrives.
- **Both new units run as root without the sandbox** of `regulus-update.service`, like its `ExecStopPost`: they exist to repair, and a sandbox mistake that cannot be seen without a real systemd (#81) would disable the repair exactly when it is needed.
- **`pending.json` is a contract between versions:** written by the version that was installed, possibly read by the one that replaced it. Fields are only added and a reader ignores what it does not know (the rule is written in `internal/update/pending.go`, with a test).
- **Not verified on a real machine:** unit ordering, the condition, and a real hard power-off (#240).

## Updates: reading the release list (audit issue #213)

One page of 30 releases could be filled by plugin releases (planned in the same repository, `plugin/<id>/vX`) or by many pre-releases, and a stable hub would then report "up to date" for ever. The list is now read 100 at a time, until a page holds a stable release of the core (the newest stable is then known, and so is every pre-release published after it), the list ends, or 5 pages were read. Only the first page is asked conditionally: if it did not change, nothing did. `/releases/latest` was not used because the beta and alpha channels need the pre-releases too, and one paginated path is simpler than two.

Withheld or stale answers (a "freeze") cannot be told from "no new release" without signed metadata that expires. That is **not done**: the hub now records when a check last **succeeded** and the Updates page warns after three days without one, which covers the common case (a hub that lost its internet access). A signed `latest.json` with an expiry was left for a later issue and is done in #263 (below).

**Done in #263: the signed index.** `latest.json` is signed with the identity of `release.yml` at a release tag (see *Updates*, "A signed index of releases"). Choices: (1) **same identity as `checksums.txt`**, as the issue asked, so a hub trusts one workflow and no second signing identity exists; the price is that a refresh has to run the release workflow *at a tag*, which `refresh_only` does, and that a release made before this cannot be refreshed. (2) **The index is attached to a release, and the hub reads the one on the newest release that has it**, verifying it for that release's tag and requiring the file to say the same tag, so the file's own words never choose the identity to check against. (3) **Replay and expiry are separate:** the hub keeps the newest `issued_at` it verified (in the update state) and refuses an older index; an index also stops being believed at `expires`, at most 90 days after it was issued (21 in practice, renewed weekly). (4) **A hidden release is detected by comparison:** the index names the newest tag per channel and the hub compares it, for the channels it follows, with the list of releases; a stable hub is not told about an alpha. (5) **No index is silent only until one was seen**: older releases carry none, and a warning on every existing hub the day this ships would be noise; once a hub has verified one, a missing index is a warning, so stripping it does not work. (6) The check **never blocks an update** the list offers: it is a warning, because a failed index (a rate limit, a missing asset) must not stop a security fix that the list does show. (7) The jobs keep the split of #206: the file is made where there is no signing identity and signed where nothing is built. **Not verified:** the workflows have not run (a tag is needed), and `refresh-latest.yml` waits for the approval of the `release` environment each week, which may need a policy decision if that is too much for the maintainers; the unit tests cover the hub's side and the generator.

## Updates: the rollout judges a server after the helper's stability window (audit issue #211)

The rollout counted a server as updated on its first connection with the new version, and as failed on any reconnection with another one. The helper on the server keeps watching for its `Stable` period after the agent connects, so a server could be counted as updated and then be rolled back (and a large wave went on past the failure), and a network blip before the helper ran stopped a rollout whose update then installed. Choices:

- **Success is a session with the new version that lasts `settle`** (30 s: the helper's 15 s plus its polling and the reconnection). **Failure** is a return to another version after the new one was seen, or, when `returnTimeout` (10 min) ends, no session with the new version. A session with the old version alone is **inconclusive** until then. So a rollback the hub never saw the new version of (the new agent could not connect) is reported after 10 minutes instead of at once: slower, but never wrong.
- **The hub watches connections, not only the registry** (`agentServer.watch`): a new version that is rolled back seconds after it connected would otherwise fall between two looks.
- **Persisted in `settings`** (no migration): the last rollout as JSON (`rollout.last`) and the failed version (`rollout.failed_target`). A failure stops the automatic mode for that version **whoever started the rollout** (before, only an automatic one), and a rollout that ends `done` clears it. A rollout running at a restart is loaded as `stopped`, its waiting servers as the new status `unknown`. A saved rollout to another version than the hub's is not shown (the page would read it as one to the current version).
- **A stop leaves `unknown`**, not `failed`, for a server that already had the update: what it does with it is not known.
- **Not done:** the agent reporting the helper's `result.json` in its next `Hello`, which would give the real outcome instead of an inference from versions and time; it touches the update contract (an added field), so it is a separate issue.
- The shared `WaitGroup` of the rollout (a `Wait` in `StopRollout` could race with an `Add` in `StartRollout`) became a `done` channel per run.

## Updates: a hub without its status socket can still be updated (audit issue #312)

The root helper judged a hub healthy only through the local status socket, which the hub treats as optional (it runs without one when the path is longer than 107 bytes, or the socket cannot be made). Every update of such a hub was rolled back. Of the two ways the issue offers, the helper now accepts a second signal (option a), and does not merely warn (option b): the hub writes `<data_dir>/running.json` (version, start time, and why it has no socket) each time it starts serving, and the helper reads it when the socket does not answer, with the same rule as for an agent's `connected.json`: only a start after the restart counts, and the service must stay active for the stable period. `/healthz` was not used because the helper would have to read the hub's configuration (address, TLS) to reach it, and a listen address may not be reachable from the machine itself. The socket stays the first choice, because an answer proves the hub serves requests, not only that it got as far as starting. The file is a helper file (a contract between versions: add only). A rollback message names both the socket and the file.

The administrator is told (#338): `GET /api/updates` carries `status_socket`, the reason from `running.json` (absent while the hub has its socket), and the Updates page shows it in English and Italian with what it means: `regulus status` shows no live data, and an update **from** a release that does not yet write `running.json` rolls back on such a hub. The hub hands the reason to the update manager when it starts serving (`Manager.SetStatusSocket`).

## Updates: concurrent stagings share the cache (audit issue #314)

The hub stages releases from two places that can run at once: its own download (the background cycle or the **Download** button, serialised by the manager) and `EnsureRelease`, called when a rollout to the agents starts. Each staging ended with a prune that removed every entry it did not keep, the other staging's `.stage-*` work directory included. The `Stager` now remembers the work directories of the stagings in progress and the prune skips them; the move into place and the prune are one step under a mutex. The downloads themselves are **not** serialised: a slow download of a new release must not hold up a rollout that needs only the archives of the running version. What is still possible, and accepted: two stagings of two versions that are both neither kept (`Keep`, the running version) nor the newest can prune each other's finished directory; the hub never stages two such versions at once.

## Certificate end dates: kept, shown and warned about (audit issue #245)

Agent certificates last five years and the CA twenty, with no renewal (#128), and nobody was told when one ends. Choices:

- **The agent's end date is stored, not recomputed.** `agents.cert_not_after` (migration 0010, both backends) is written at enrollment from the signed certificate. Agents enrolled earlier are filled in from the certificate they present on their next connection (only when its serial is the one issued for them); the hub does not keep agent certificates, and computing `created_at + 5 years` would be a guess. Until then the date is unknown and counted in `agents_unknown`. The agent protocol is unchanged.
- **One endpoint for the hub-level dates, one field per agent.** `GET /api/certificates` for the CA, the listener, the soonest and the warnings; `cert_not_after` in the existing agent answers for the Servers page. It needs `servers.manage`, like the other trust settings (tokens, the listener): renewing is that permission's job, and a viewer has nothing to act on.
- **What is warned about:** the CA and agents that are not revoked, within 90 days or already ended. The listener is not: it renews itself 30 days before its end (#204). The warning carries data only; the dashboard writes the text in both languages.
- **One log line a day**, not one per certificate: checked every hour, logged at start and then at most once in 24 hours while something ends soon. A restart logs it again.
- **Not verified on a real machine:** the dates shown on a real install and the daily log line under journald (to be added to the certificate test, #241).

## A dead hub connection: keepalive, and gaps instead of a replay buffer (audit issue #222)

Before, nothing on the agent connection had a keepalive: an agent whose hub lost power, or whose NAT silently forgot the flow, believed it was connected until TCP gave up (about 15 minutes), while the hub had long called it offline.

- **Keepalive on both ends, from one set of numbers** (`internal/protocol/keepalive.go`). The agent pings when it has read nothing for 30 s and drops the connection when the answer does not come within 10 s, also with no stream open (between two sessions); `Run` then reconnects as usual. The hub's enforcement policy allows a ping every 15 s at most (half the agent's interval, so a future agent may ping somewhat more often without being cut off by today's hubs) and pings without a stream; a client that pings faster is disconnected with gRPC's `too_many_pings`. The hub also pings a connection it has read nothing from for 30 s and closes it after 10 s without an answer; an agent sends a heartbeat every 15 s, so this only fires for a dead one. A test checks that the two ends agree and that a dead hub is noticed within 45 s.
- **A contract between versions.** The numbers are listed in [versioning.md](versioning.md): the hub's minimum must never rise above the interval of an agent it serves. A gRPC client disconnected with `too_many_pings` doubles its interval for that connection, so an agent that meets a hub without this policy (none was released) loses its connection a few times and then settles, instead of being cut off forever.
- **Samples while the hub is away: gaps are accepted, nothing is replayed.** A buffer of reports flushed on reconnect was weighed and not chosen now: the hub stamps a sample with the time it *received* it (the report's `collected_at` is used only to compute the network rates between two reports, and trusting an agent's clock for the history is a choice of its own), its report rate limit would drop a burst of old reports, the store keeps samples in arrival order, and the history it would fill is kept only in memory for one hour and lost at every hub restart anyway. What an agent collects while it cannot send is dropped (the collection is skipped when no session is up); the dashboard's charts show the gap. Revisit together with a persistent metrics history: that is when a replay that uses `collected_at` is worth it.
- **Tested** with a TCP proxy that stops forwarding without closing (the kernel still acknowledges what the agent sends): with gRPC's shortest ping interval (10 s) and a 1 s timeout the agent is connected again in about 11 s, with the production numbers in about 40 s (`REGULUS_SLOW_TESTS=1`, not run in CI because of its length). Raw HTTP/2 pings faster than the policy get `GOAWAY ENHANCE_YOUR_CALM`, pings within it are answered. **Not verified on a real machine:** a hub host that loses power, and a real NAT that drops the flow.

## Agent port: a global metrics budget, deny by default and a cap on live streams (audit issue #244)

What was left over from the limits of #199:

- **A memory budget for the whole metrics store**, not only per agent: about 256 MiB, estimated from the encoded size of each report (four times the wire size plus 256 bytes, measured against the Go heap with reports of 0, 4 and 64 disks and interfaces; a test keeps the estimate within 25 % of the heap the store really holds). Over the budget, the **oldest samples of any agent** go first, so with many agents (or one that reconnects under new identities) every history gets shorter evenly instead of one agent losing everything; the newest sample of each agent is never dropped, since it is the agent's current state (one report is at most 256 KiB). Eviction costs one pass over the agents per dropped sample, the same order as the retention pass every report already makes. The number is a constant, not a setting: 256 MiB keeps a full hour for about 500 small hosts; make it a setting when someone needs more.
- **Keepalive policy**: written together with the agent's keepalive in #222 (see above), so the two agree; the policy refuses a client that pings more often than every 15 s.
- **Deny by default for unary calls**: a unary interceptor checks the agent's certificate on every unary call except those listed in `openUnaryMethods` (only `Enroll`). Tested with a dummy unary service registered on the real listener: no certificate gets `Unauthenticated`, a revoked agent `PermissionDenied`, an enrolled one gets through.
- **At most 16 live streams per user** on `/api/stream`. The extra one is **refused** with 429 rather than the oldest closed: two windows of one user over the cap would otherwise close each other in turn for ever, each reconnecting. The dashboard opens one stream per tab and retries a refused one with its usual backoff; it does not say why (a WebSocket that fails its handshake gives the page no status code).

## Fuzz tests for the /proc parsers and the network rates (audit issue #228)

- **Six fuzz targets, seeds in the code.** `FuzzParseCPUTimes`, `FuzzParseMemInfo`, `FuzzParseMounts`, `FuzzParseNetDev`, `FuzzUnescapeMount` (`internal/agent/collector_fuzz_test.go`) and `FuzzNetworkRate` (`internal/hub/rate_fuzz_test.go`). They check invariants, not exact values: busy time within the total and a CPU share between 0 and 100, used plus available equal to the total, one mount per device of a real filesystem, interfaces named, not `lo` and listed once, mount paths that decode back to what the kernel encoded, and network rates that are either absent (a counter went back, the interval cannot be trusted) or finite, non-negative and exact. Their seeds are `f.Add` calls, so every `go test` runs them; inputs a fuzzer finds go under `testdata/fuzz/<Target>`, or become a named unit test as below.
- **Nightly, not per pull request.** `.github/workflows/fuzz.yml` runs each target for 30 seconds every night (and by hand); `make fuzz` does the same locally. Fuzzing on every pull request would add minutes without finding much more.
- **What the fuzzers found, now fixed:** a `/proc/stat` line whose counters overflow 64 bits gave busy time larger than the total (now an error); a `/proc/meminfo` value in kB that does not fit in bytes wrapped to a small number (now skipped, and the old-kernel fallback sum saturates); `/proc/net/dev` lines without a name, or a name twice, were reported (now skipped: the hub pairs counters by name). None of these come from a real kernel. `unescapeMount` was suspected of mishandling an escape at the very end (`a\040`); it does not, and a test keeps it so.
- **Not done:** memory inside a container (cgroup v2, LXC) is still the host's. Both are left for separate issues.

## Containers: the agent reads its cgroup limits (#325)

In a container the agent reported the host's memory and CPU count. It now reads the limits of its own cgroup, but only when it detects a container (`internal/agent/cgroup.go`):

- **Only in a container.** On a real server the agent's cgroup is its systemd service, and a `MemoryMax` on the service is not the server's memory. The detection is the one that already fills `container` (`/run/systemd/container`, `/.dockerenv`, `/run/.containerenv`), which a container the agent cannot recognise escapes: it keeps the host's figures, as before.
- **Both versions of cgroup.** v2 (`memory.max`, `memory.current`, `memory.stat`, `cpu.max`) and v1 (`memory.limit_in_bytes`, `memory.usage_in_bytes`, `cpu.cfs_quota_us`). v1's "unlimited" is a huge number, not a missing file, and is read as no limit. A container with its own cgroup namespace sees its group as the root of the mount; otherwise the group is found from `/proc/self/cgroup`, and the groups above it are read too, the lowest limit winning.
- **Memory used is `current` minus `inactive_file`**, as `docker stats` does, so the page cache that can be given back does not look like pressure. Total and available follow from the limit. A limit above the host's memory is not a limit.
- **CPU usage and swap follow the cgroup too (#355).** CPU usage is the CPU time of the group between two reports (`usage_usec` of `cpu.stat` in v2, `cpuacct.usage` in nanoseconds in v1) over the elapsed time, divided by the quota, or by the CPUs the agent may run on when there is no quota (`runtime.NumCPU`, which follows `cpuset`). The first report, and any over less than one second, keep the host's figure from `/proc/stat` and do not move the previous reading. Swap is `memory.swap.max` and `memory.swap.current` (v2; `max` is no limit, 0 is no swap), or in v1 what `memory.memsw.*` has beyond the memory figures (nothing is read when the kernel has no swap accounting). A swap limit above the host's swap is not more swap; a group without a limit keeps the host's total and shows its own use. **The load average stays the host's:** the kernel has no per-cgroup load average, and the System widget says so.
- **Not done:** the load average (no source). The reading was checked against fixtures for v2 and v1 and on this build's own cgroup v1 container; a Docker with a `--memory` limit on a real host has not been tried, which is the `[Test]` issue for #325.

## CPU unknown is null, not 0 (#340)

An agent that cannot read `/proc/stat` sent a CPU share of 0 and looked idle. The signal was already in the report: such an agent lists `cpu` in `MetricsReport.unavailable` (#230). Choices:

- **No protocol change.** The issue proposed making `usage_percent` optional. Changing a singular proto3 field to `optional` changes its presence, and `buf breaking` (the rule of `docs/versioning.md`) reports it as breaking, so it was not done. The list `unavailable` already says the same, is add-only, and an agent that wrote it before this change is covered without being updated.
- **The hub turns it into null.** `cpu_percent` in `GET /api/agents/{id}/metrics` and in the stream is `null` when the report lists `cpu`, a number otherwise (`internal/hub/api.go`, `cpuPercent`; OpenAPI says `[number, "null"]`). A `?step=` bucket averages the reports that have a value and is `null` when none has. An agent from before #230 does not list anything and still reads as 0; nothing can tell that case apart.
- **The dashboard shows it as not available.** `MetricsPoint.cpu_percent` is `number | null` (a missing or non-numeric value is still refused), the CPU widget says "not available" for a null latest point, and the chart leaves a gap for a null in its history.

## An end-to-end test with the real binaries (audit issue #233)

- **A Go test, not a shell script.** `internal/e2e` drives the processes from Go, so it can also act as a misbehaving agent over the real listener (a Hello with another protocol version, a certificate from another CA or expired) with the project's own `pki` and generated client, which a shell script could not without extra tools. `scripts/smoke.sh` stays for the packaged binary (dashboard, console, configuration, admin reset) and keeps its short enroll-and-revoke check.
- **Run on every pull request, in its own job.** Gated by `REGULUS_E2E=1` so that `go test ./...` stays fast; `make e2e` and the CI job `e2e` set it, and the job fails if the test was skipped. It takes about 30 seconds after the build; the binary is built with `-race` and a data race in any process fails the test.
- **The agent listener has a fixed port per run** (a free port picked by the test), because a restarted hub on port 0 would get another port and the agent would have nowhere to reconnect.
- **The agent of the previous release (#341).** `TestAgentOfAnOlderRelease` downloads the newest published release's agent (checked against `checksums.txt`, not its signature) and runs it against a hub of this source built with `-X main.version=<old minor + 1>` and `<old minor + 2>`: the first admits it as `behind` and shows its metrics, the second admits it to an update-only session. Run against `v0.2.0-alpha.1` in the cloud session that wrote it. It is the one test that needs the network, so it skips with its reason when it cannot get a release, and CI accepts that one skip as a warning; a skip anywhere else still fails the job. Run in `make e2e` it adds about a minute (two builds with the race detector).
- **Not covered,** listed in [development.md](development.md#end-to-end-test-hub-and-remote-agent): an update over the stream (a hub binary trusts only the project's Sigstore identity, so a test cannot give it a signed release; it would need a seam in the verifier that a test binary has and a release binary does not), an expired hub CA, PostgreSQL, systemd.

## Certificate kinds: every certificate of the hub CA says what it is for (audit issue #316)

Agent certificates were told apart only by `Organization: "Regulus agent"`, which nothing checked: any later certificate from the same CA (a phone in Regulus Access, #154; a hub-to-hub certificate, #107) would have passed the agent listener as an agent named after its common name, and an agent certificate could have passed a future service. Choices:

- **The kind is a URI in the subject alternative names**: `regulus:<kind>:<id>` for a client certificate, whose id must equal the common name, and `regulus:hub` for the listener certificate. Kinds today: `agent`, `hub`, and `device` reserved for #154 (nothing issues it; it exists so that the refusal is tested). A new kind is added to `internal/pki/kind.go`; exactly one `regulus:` URI per certificate. **Rejected:** a private EKU or policy OID (an OID needs a registered arc, and is harder to read with `openssl x509 -text`); an intermediate CA per kind (the right answer if #107 delegates, but more key material and more to rotate today; the URI does not prevent it later).
- **Each service accepts only its kind.** `pki.ClientIdentity` returns the kind; the agent listener uses `pki.AgentIdentity` and refuses any other kind, an unknown one, two of them, or a mismatched id with `PermissionDenied` **before** the registry is asked. A future service must check its own kind the same way. Agents refuse a listener certificate that carries a kind other than `hub`.
- **Already-enrolled agents keep working.** A certificate with **no** `regulus:` URI and the organization `Regulus agent` is accepted as an agent (`Identity.Legacy`): that is exactly what every older hub issued, and nothing else, as a client certificate, and every certificate issued from now on carries a kind, so an unmarked certificate cannot be of a new kind. Any other unmarked certificate is refused. A listener certificate without a kind is accepted too (an agent updated before its hub).
- **For how long:** while such certificates exist, that is until renewal (#128) re-issues them or they end (five years after the last enrollment on a hub older than this change). The legacy path is to be removed in the first release after #128 has re-issued every agent certificate; until then the hub counts the connected agents on a legacy certificate (#322: `legacy_agents` in `GET /api/certificates`, and one warning in the log each time such an agent connects), so the administrator can see when the last one is gone. The count is of connected agents: an agent that is off is not in it. Removing the legacy path itself waits for #128.
- **The threat models of #154 and #107** start from this rule; a line says so in [regulus-access.md](regulus-access.md) section 3 and [hub-redundancy.md](hub-redundancy.md) section 5.
- **Verified by tests only** (`internal/pki/kind_test.go`, `TestStreamsNeedAValidCertificate`): a legacy agent of a real older hub reconnecting after the update is not verified on a real machine.

## Console: network reachability and following the log (#369)

- **Reachability is checked as far as the hub's machine can.** A program on the server cannot prove that another host gets through a firewall or a router. The *Network access* check therefore tests what is local (the hub listens on more than loopback and answers on each LAN address of the machine) and says plainly that the firewall is not checked, with the URL to open from another host. A check from another host would need a second machine and stays a manual step.
- **The log is followed, with the reload as the fallback.** The Logs tab runs `journalctl -f` while it is open and stops it on leaving; if it cannot start or ends, the old reload every two seconds applies, so nothing is lost on systems where it fails. Logs without journald are #375: the hub has no log file setting, which is a design question of its own.
- Creating the first administrator from the terminal and the background-colour delay were done in the first part of #369 (`regulus hub create-admin`, `COLORFGBG` and `REGULUS_BACKGROUND`).

## Updates: a local policy, reproducible builds and provenance (#215)

- **The policy file is separate, and read by root from `/etc`.** The issue proposed `max_channel` and `max_major` in `agent.yaml` and the hub configuration. They are in **`/etc/regulus/update-policy.yaml`** instead: the root helper must not parse the configuration of the unprivileged programs (their parsers change with them, the hub's is strict about unknown keys, and the agent's `updates` is a boolean, so the two files cannot share a key), and one file serves a hub and an agent on the same machine. It is trusted only when it is a regular file owned by root and not writable by others; a file that cannot be trusted or parsed **refuses every installation** (fail closed). The limits are the helper's own, so a compromised hub cannot widen them: `/etc/regulus` is not writable by the hub's user. A policy is not created by default, because a default would change what existing servers do.
- **What it does not do.** The agent and the hub do not check the policy before they ask: the helper's refusal reaches the Updates page as a failed result. The `automatic` mode would therefore try again a version the policy forbids; it does not, because a failed result for a version is remembered like a rollback (see *Updates*), but the page shows an error that is a configuration, not a fault. A refined message on the Updates page is a possible follow-up.
- **Reproducible archives and packages.** `mod_timestamp`, `builds_info.mtime` (archives) and `mtime` (packages) are the commit time. CI builds twice from a clean build cache and compares hashes (`scripts/check-reproducible.sh`). Not covered: the SBOMs (they record when they were made), `checksums.txt` of a snapshot, and a rebuild of a published tag in a clean container, which is the stronger check the issue asks for and needs a release to exist: until it is done, "reproducible" is proved for the same commit on the same runner image, not across machines.
- **Provenance** is attested for archives, `.deb` and `.rpm` in the publish job, which already holds `id-token`; the bundle is published as `provenance.sigstore.json`. It adds `attestations: write` to that job. No Regulus program checks it.
- **The helper's state is removed on purge**, and `data_dir` outside the default is documented as unsupported for dashboard installs: making the path units follow a custom directory needs the units generated at install time, which is a larger change than the finding.

## Metrics for Prometheus (#389)

`GET /metrics` serves the hub's figures and the latest figures of each connected server in the Prometheus text format ([Metrics for Prometheus](metrics.md)). Choices:

- **Hand-written, no library.** The text format is a `# HELP` and `# TYPE` line per metric and one `name{labels} value` line per sample; `internal/hub/prometheus.go` writes it in about 60 lines and a test checks every line against the grammar. The official client library would add a dependency tree and a registry for a few dozen figures that the hub already holds in memory; it is worth reconsidering if histograms are ever needed.
- **Off by default, a separate bearer token.** The endpoint is outside `/api/` and outside the session login, because a scraper cannot sign in. It is served only with `prometheus.enabled` and a token of at least 32 characters in `REGULUS_PROMETHEUS_TOKEN` (the environment only, like the database password: never in the file, masked by `regulus config`, the hub refuses to start without it). The token is compared in constant time (on SHA-256 hashes, so its length does not leak) and a refusal sends nothing but `401`. A scoped API token would be better than one shared secret, but the API token design is not decided; this setting does not block it. The listener is loopback by default, so the port is not open to a network unless the administrator opens it.
- **Labels: `id` and `server`.** `id` never changes, `server` is the display name for people. Disks add `mount` and `filesystem`, networks `interface`. A rename of a server makes a new series with the same `id`; queries that must survive a rename match on `id`.
- **Cardinality is bounded in the hub:** at most 32 filesystems and 16 interfaces per server, the first ones of the report, and `regulus_server_series_cut` shows when some were left out. Without a bound one server with hundreds of container mounts would decide the size of the monitoring system.
- **Counters are per process**, so they restart at 0 with the hub; database latency is the last measured value (the 15-second ping and the once-a-minute presence write), not a histogram: a scrape every 15 to 60 seconds sees a sample of it, not all of it.
- **Not verified:** a scrape by a real Prometheus. The format is checked by a grammar test, not by `promtool check metrics` (the `[Test]` issue is #394, which also asks whether a scoped token should replace the shared one).

## Updates: a PostgreSQL hub is not refused without a backup (#383)

A hub on PostgreSQL can have its program replaced but not its database put back (the helper cannot copy a server). The question left over from #247 was whether the helper should refuse to update such a hub unless the request says "I have a backup". **Decision: no, it stays the administrator's call.** Reasons:

- The risk exists only when a release has a **strict** migration (one an older program refuses). The project's rule is that a release's migrations are expand-only, a test fails for one that is not, and `TestPreviousReleaseServesOnTheCurrentSchema` (CI) runs the real previous release on the migrated schema (#383). A strict migration is a deliberate, listed exception and belongs in the release notes.
- A confirmation on every update, whatever its migrations, teaches administrators to tick it. The automatic mode applies updates with nobody there to tick, so the rule would either block automatic updates on PostgreSQL or have an exception that defeats it.
- The Updates page already says what a rollback does not restore on PostgreSQL ([Updates](updates.md#what-a-rollback-puts-back-and-what-it-does-not)).

**Revisit** when the first strict migration is planned: the release that carries it can make the helper refuse on PostgreSQL unless the request names the backup, because only then is the refusal about a real risk. Until then no code changes.

## Browser tests: Playwright outside the dashboard project (#390)

The dashboard's own tests (vitest, jsdom, a fake `fetch`, fake sockets) do not start the hub, so a broken build, a wrong header or a Content-Security-Policy that blocks the real page is not seen until a person looks. `make browser-test` runs the real hub binary with the dashboard built in, real agents and Chromium ([Development](development.md#browser-tests-the-dashboard-in-a-real-browser-390)). Choices:

- **Node's test runner and the `playwright` library, not `@playwright/test`.** `@playwright/test` as a dev dependency of the dashboard would add the runner, its lockfile entries and a browser download to every `npm ci` (`make test`, `make lint`, the packaging build). The library alone, installed in the CI job and found through `NODE_PATH`, is what `scripts/browser-load.mjs` (#370) already does. What `@playwright/test` gives that this does without: traces and screenshots on failure are written by `keepFailure` in `scripts/browser-test/harness.mjs`; retries and parallelism are not wanted (the scenarios share one hub and run in order, so a flaky one should be fixed, not retried).
- **One hub, scenarios in order, each in its own browser context.** The first scenario creates the admin through the page, which is itself something to test; the others need that admin. A scenario that fails does not leave state that changes the next one: contexts do not share storage.
- **Network interception only for what the hub cannot be made to do on demand:** a `429` with `Retry-After` and one `503`. A wrong password and a right one go through the real hub.
- **Not verified:** Firefox and WebKit (Playwright can run them, but the CSP and the stream differences are what #281 asks a person to look at, and this adds two downloads to CI; worth adding when a browser-specific bug is found: #393), a screenshot comparison (it would need a reviewed baseline per platform), and the job on a real CI runner: it ran locally against the preinstalled Chromium.

## Database: SQLite by default, PostgreSQL by configuration

Done in #122. Choices, so they are not rediscovered:

- **Driver:** `github.com/jackc/pgx/v5` through its `database/sql` adapter. Pure Go (the binary stays static, no cgo), MIT licence (compatible with Apache-2.0). It was already in the module graph as an indirect dependency.
- **One place knows the dialect.** Option (a) of the issue: **separate migration directories per backend** (`migrations/sqlite`, `migrations/postgres`, same numbers and names) with a test that compares the resulting schema, plus a small **`Rebind`** in the PostgreSQL connection wrapper that turns `?` into `$n`, so none of the 80 call sites changed. Rejected: one portable SQL set plus a rewriter (SQLite `STRICT`, `INTEGER PRIMARY KEY`, `COLLATE NOCASE` and the table rebuild of migration 9 cannot be written once).
- **Portable SQL in the code:** `INSERT OR REPLACE` became `INSERT ... ON CONFLICT (user_id) DO UPDATE`; `LastInsertId` (not supported by pgx) became `INSERT ... RETURNING id`; unique violations are recognised by `storage.IsUniqueViolation` on both; parameters in the select list of an `INSERT ... SELECT` are cast (`CAST(? AS TEXT)`) because PostgreSQL cannot infer their type.
- **Time and value representation:** unchanged. Timestamps stay ISO-8601 text and flags stay integers in PostgreSQL too, so every code path is identical on both backends. Row ids are `BIGINT` identity columns. Cost: no `timestamptz` arithmetic in SQL, and a later move to native types is a migration of its own.
- **Case-insensitive names** (`COLLATE NOCASE` in SQLite) use the **`citext`** extension in PostgreSQL, created in `public` with `public` kept on the search path. Alternatives rejected: nondeterministic ICU collations (not usable in foreign keys before PostgreSQL 18), and `lower()` indexes (would need every query and the `roles` foreign key changed).
- **Migrations on PostgreSQL:** transactional DDL; the same "refuse a newer schema" rule; a session **advisory lock** around the whole run. The `-- regulus:no-foreign-keys` mechanism is **not** needed there (the constraint is dropped in place), so it is ignored on PostgreSQL.
- **Connections:** SQLite writes on one connection and the hub reads on a separate pool of 4 (#219, below). PostgreSQL uses a pool (10 open, 4 idle, 30 min lifetime, 5 min idle) and waits up to 60 s for the server at start. A running hub does not exit when the database goes away; it logs the change of state once and reports it in `regulus status` and the console and in the dashboard (#140): a banner fed by `GET /api/database`, a public endpoint with one boolean, because sessions live in the database and an endpoint that needs a login cannot report that the database is down. `/healthz` is deliberately unchanged (the installer, the smoke test and the update helper wait for `ok`). The banner texts are in English and Italian in one file until the translation mechanism of #125 exists.
- **Password:** environment only (`REGULUS_DATABASE_PASSWORD`, normally `/etc/regulus/regulus.env`, `0640 root:regulus`). It is deliberately **not** a YAML key, so `config.yaml` (which `regulus config set` rewrites and which may be copied around) can never hold it and the strict YAML parser rejects it. Shown as `********` when set.
- **Open questions of the issue, answered:** minimum PostgreSQL **14** (Ubuntu 22.04; tests run on 14 and 16); default `sslmode` is **`prefer`** (works for a local server; `verify-full` plus `database.sslrootcert` for a remote one); schema is **`public` by default**, configurable with `database.schema` (which must exist).
- **Check command:** `regulus db check` (name confirmed here), see [Database](database.md).
- **CI:** a PostgreSQL service job runs the whole suite with `REGULUS_TEST_DATABASE_URL`; each test gets its own schema (`storagetest`).
- **CI coverage (#141, partly):** the PostgreSQL job is a matrix over **14 and 16** (check names carry the version, for example `Go tests on PostgreSQL (14)`; a branch protection rule that requires the old name `Go tests on PostgreSQL` must be updated). A second job, `Go tests on PostgreSQL with TLS (verify-full)`, generates a CA and a certificate for `localhost` with openssl, starts `postgres:16` with `ssl=on` (key `0600`, uid 999) and runs `TestPostgresVerifyFull*` through `storage.Check` and `storage.Open`: the right CA connects over TLS; a wrong host name (127.0.0.1), a root that is not the issuer and a missing root file are refused; the password is not in any message. **Still not verified:** an install on a real VM, `apt` upgrading an existing PostgreSQL, a database on another host (real network, real certificate chain), `verify-ca`, and PostgreSQL versions other than 14 and 16. #141 stays open for those.

## Installer: the database choice (#123)

- **Scope.** By default the installer **connects to an existing PostgreSQL** that the administrator prepared (`docs/database.md` has the SQL). Installing it locally is the opt-in `--db-local` (#139, below).
- **Flags, not a URL.** A single set of options (`--database`, `--db-host/-port/-name/-user/-sslmode/-sslrootcert`) rather than one connection URL read from a file: each option is validated on its own with a specific error, and the values map one to one to the `REGULUS_DATABASE_*` settings. The password has no option: `--database-password-file`, `REGULUS_DATABASE_PASSWORD`, or a prompt without echo.
- **Where the password lives.** Only `/etc/regulus/regulus.env` (written `0640`, then `root:regulus` by the package's post-install script), in double quotes with `\` and `"` escaped as systemd and `regulus db check` read them. Never `config.yaml`, which the hub refuses to read a password from anyway.
- **The check runs before the install.** The issue asked for the check after the install; the installer does it *also* before, with the binary extracted from the verified `.deb` (`dpkg-deb -x`) and the settings passed in the environment of that one process, so a wrong password or a missing database stops the run while nothing has changed. The check after the install, with the installed binary, reports and fails the installer with instructions but does not roll back the package.
- **Post-install script when the database is unreachable.** It prints the result of `regulus db check` and the way to fix it and **never fails the package**. The service is still enabled and started: the hub waits 60 s for the database, exits, and systemd restarts it every few seconds after that (`Restart=on-failure`), so it comes up by itself when the database does.
- **Upgrades.** An installation is recognised by the installed package, the SQLite file or database settings in the environment file. Without `--database` its backend is kept and nothing is asked or written; naming the other backend stops with a pointer to #124 before anything is downloaded.
- **Not verified:** the installer has not run on a real VM with PostgreSQL (#81), and not with `apt` upgrading an existing PostgreSQL install. The script is tested with stubs for `dpkg-deb` and the binary, and by hand against a PostgreSQL 16 with SCRAM authentication using the real binary (wrong password stops, right password writes the file; a password with quotes, a backslash and `$` round-trips).

## Regulus Access: direction (not final; epic #152)

Agreed in conversation on 2026-11-13, **proposed**, to be confirmed in the design issues of #152. Nothing is implemented. Recorded here so the reasoning is not lost:

- **The phone connects to the hub, not to the nodes.** It is always the client, so mobile networks and NAT do not matter, and no node opens a new port. Identity is a device certificate from the group's CA with the key in the Android Keystore; mTLS over TLS 1.3 already encrypts, so no extra encryption layer. mTLS does not depend on the phone's address.
- **Rejected for the first version:** a public Access listener on every node (multiplies the attack surface), and a mandatory overlay network (Tailscale, WireGuard): not needed for security. The overlay stays an optional way not to expose anything.
- **Away from home: the access gateway** (#161), a public node that forwards the phone's connection to the active hub. mTLS stays end to end phone to hub; the gateway holds no secrets. It follows a failover to the redundant hub. Its extra capabilities: notifications (second step) and authentication for other programs (later, **separate design**, because it would make a public machine hold keys).
- **At home: the local address first** (#162), as an ordered address list with the CA fingerprint checked on every path; no discovery in the first version.
- **Node types** are one role plus capabilities, and every node keeps the same connection to the hub inside; see [node-types.md](node-types.md) (#160). Direct node-to-node links are left for later and, when they exist, are authorised by the hub.
- **Passkeys (#50)** stay for the web login; Access uses the device key.
- **Free-tier cloud servers:** a plugin to measure use and optionally keep a server active (#163) is only built after the provider's current terms are read.

## Installer: a local PostgreSQL (#139)

- **Opt-in, `--db-local`** (implies `--database postgres`), plus **`--db-reuse`** for an existing role and database. The default stays "connect to what you prepared".
- **Creates only its own role and database** over the local socket as the `postgres` system user, on `127.0.0.1`; it never alters an existing role or database. It **refuses** when either exists, because it could not know their password and must not reset it; `--db-reuse` is the explicit "I know, use them" and then needs the password given, never generated.
- **The password** is 32 letters and digits from `/dev/urandom` (nothing to quote in SQL or in the environment file), sent to `psql` on **standard input**, never an argument, never printed, stored only in `/etc/regulus/regulus.env`.
- **Order, so a second run works.** After the verified download the installer creates the role and database, then **writes the settings**, then runs the check with the binary from the package. If the check fails the password is already saved, and a re-run finds `REGULUS_DATABASE_TYPE` in the environment file and keeps it (nothing is created twice) instead of finding a role it has no password for. A failure leaves PostgreSQL, the role and the database in place; the message says so.
- **Re-run on an existing installation:** `--db-local` is ignored with a note; on a SQLite installation it is refused like `--database postgres` (#124).
- **Tested** by `scripts/test-install.sh` with stubs for `apt`, the `postgres` user and `psql` (including that the password is on no command line), and by hand: the real functions against a throwaway PostgreSQL 16 cluster (role and database created and owned by the role, `citext` enabled, login over TCP with the generated password, a second run refused). **Not verified:** `apt-get install postgresql` on a real Ubuntu VM, PostgreSQL 14 from 22.04, a cluster that is stopped or on another port, and the whole installer end to end with a release (#81, #141).

## GUI translations: dashboard mechanism (#125, proposal in progress)

- **No library:** two typed catalogs (`dashboard/src/i18n/en.ts` is the source, `it.ts` is `Record<keyof en, string>`), so a missing Italian text is a compile error, plus a test for extra keys, empty texts and placeholder mismatches. Keys are stable dotted names, not the English text. No plural machinery (two keys where a count matters); dates and numbers through `Intl`.

The help line is built from parts (`HelpMain`, `HelpReset`, `HelpQuit`) instead of cutting an English substring out of it. The parity tests now compare the fmt verbs in order (`%d`, `%s`), and the maps key by key.
- **`cmd/regulus` texts are CLI, English only (#191).** What the command prints itself, the usage and flag help, the `regulus: …` errors, the notes on standard error after `config set`, and the reason the console did not open, is the command-line interface, not the GUI, so the language rule keeps it in English: one text to search for in issues and logs, and the same as the errors that come from Go and `internal/config`, which have no translation. The reports meant for people that the commands print on standard output, the text of `regulus status` and of `regulus config list`, come from `internal/console` and follow the locale.
- **Setting errors carry a code (#318).** `config.Normalize`, `SetFile` and `SetFileForce` return a `*config.SettingError`: a stable code (`config.ErrorCode`, such as `port` or `choice`), its arguments and, for file errors, the underlying error. `Error()` is the English text, prefixed with the key, which `regulus config set` prints as before (CLI, English). The console maps the code to a template of its own table (`SettingErrors`, English and Italian), so the Settings tab shows the reason in the console language; a test fails when a code has no template, or a template has a different number of verbs than the code has arguments. What stays English inside a translated sentence: the operating system's reason when the file cannot be read or written, and the reason `Config.Validate` gives for a file that was already invalid elsewhere (the one way a valid value breaks a valid file, PostgreSQL without a host, has its own code). The console's texts differ from the CLI's where the CLI's would be wrong there (the data directory refusal points to `regulus config set ... --force` instead of "repeat the command with --force").
- **`config set` removes the temporary files a killed writer left (#399).** `writeConfig` writes `.config-*` and renames it; a `kill -9` or a power cut between the two leaves a full copy of the configuration. The next write deletes the `.config-*` regular files in the same directory that are older than ten minutes and have the owner of `config.yaml`. A younger one may belong to a writer that is still running, so it stays. Mode `0600` until the rename is unchanged.
- **`keep_old_listen` runs only across the loopback change (#397).** The package keeps `:8080` for a hub that listened on every interface (#197) only when the version being replaced is older than 0.3.0, the first release with the loopback default: `$2` for dpkg, `rpm -q` of the old package in `%pre`. An unknown old version acts as before. Without this check every upgrade read a deleted or commented `listen` line as the old default and wrote `REGULUS_LISTEN=:8080`, reopening the dashboard over plain HTTP.
- **Package script fixes from the audit (#398).** `postinstall.sh` runs only for `configure`, `1` and `2` (the `abort-*` actions of dpkg exit at once). `preremove.sh` leaves `/etc/regulus/.removed` and `postinstall.sh` treats its presence as a fresh install (enable and start, then delete the marker), because dpkg gives the last configured version to the install that follows a `remove`; a purge deletes the marker. On Debian the group is created first (`addgroup`) and the user joins it (`adduser --ingroup`), so a group left without its user does not stop the install. The `.rpm` depends on `shadow-utils` for `useradd` and `groupadd`. **Accepted: rpm has no purge**, so `rpm -e` leaves `regulus.env` and the other settings files; the package manager convention is that an erase keeps configuration, and `docs/installation.md` says what to delete. Not checked: the order of `0.1.0-beta.1` and `0.1.0` in the rpm version (nfpm may need a `~`), left to #401.

The older version for the upgrade checks is a stand-in built from the same scripts. Not covered: the units under real systemd, SELinux, the `.rpm` and arm64 (#273, #401). The script was written without a container runtime in the session that added it and has not been run yet: the first CI run is its first run.

Whoever adds a feature that lists interfaces adds `AF_NETLINK` with it.
- **Signing identity across a move (#392).** v0.1.0-alpha.1 and v0.2.0-alpha.1 are signed as `CodexCircle/Regulus`, v0.3.0-alpha.1 as `Stellatinus/Regulus`, and an installed server pins the identity of its own build, so the older ones cannot update to the newer ones by a rollout; this is written in `docs/releases.md` (a table) and `docs/updates.md`, with the manual way (the installer of the new release). **No permanent allowlist of identities:** it would let whoever controls an abandoned organization sign for every server, and it would not help the servers that already exist, which cannot learn a new identity from a release they refuse. A future move needs a bridge release (signed by the old identity, accepting the new one) installed before the first release of the new identity. **The hub does not hide servers it expects to fail:** the only fact it has is the version number, and a hard-coded cut-off would be wrong the day another move happens; the rollout fails for them with the signature message and stops. `TestUpdateOfAnOlderAgentOverMTLS` skips with this reason and will run to the end on the first pair of releases signed by the same identity (v0.3.0-alpha.1 and the next one).
- **Plugin widgets run in a sandboxed frame, never in the dashboard's page (#315).** A module from the hub's origin would run with the viewer's session and could call any API the viewer can, so the manifest's permissions could not bind it. Widgets run in `<iframe sandbox="allow-scripts">` without `allow-same-origin` (opaque origin, no cookie), served with a `sandbox` Content-Security-Policy of their own and no `connect-src`, and talk to the dashboard only by `postMessage`; the dashboard turns each message into an API call for the plugin id, which the hub checks against the approved permissions and the viewer's own. Read-only first. No exception for first-party plugins. This was written ahead of any code and is a proposal in the sense of AGENTS.md: it is the default #21 starts from, and a better design can replace it in that issue. Details in `docs/plugins/README.md`.
- **Alerts: evaluated on the hub, quiet by default, one delivery package (#386).** Rules read data the hub already has (presence, the last report, the metrics history, certificate dates, rollout state, the active-hub lock); nothing new runs on the servers. Defaults fire only after a duration (an offline agent after 5 minutes, a disk at 90% for 10 minutes), CPU and memory are off until an administrator sets a threshold, and a server that is offline raises that one alert and no others. One message per change of state, with a recovery time against flapping and an optional reminder. Email and webhooks live in one package that #112 and #157 reuse, and a channel lists which kinds of event it takes. The SMTP password and webhook secrets are stored encrypted with `secret.key`, never in `config.yaml`. A hub that is down raises nothing: that is #112, and the advice for a single hub is an external check of `/healthz`. Full design in `docs/alerts.md`.
- **Persistent metrics history: two tiers of buckets, written once a minute (#387).** The raw reports stay in memory for the live charts. The hub writes completed buckets to the database in one transaction a minute: 1-minute buckets for 3 days and 15-minute buckets for 90 days (both settings), pruned in batches like the audit log; per-disk history is separate (#149). The receive time stays the stamp; the agent's `collected_at` is trusted only for a replayed report inside the replay window and later than the last stored bucket (#334), so a wrong clock cannot rewrite the past. A request returns at most 1,000 points and picks its tier from `step`. The backup leaves the tables out by default. Design in `docs/architecture.md`, section 5.
- **API tokens: bearer, hashed, a subset of the owner, never step-up (#388).** `rgt_` plus 32 random bytes, shown once, stored as SHA-256; sent only in the `Authorization` header; effective permissions are the token's list intersected with the owner's current ones, read-only by default; a route that asks for step-up refuses every token, so accounts, roles, enrollment, revocation and updates stay with a person and a second factor; `tokens.create` and `tokens.manage` are new permissions; audit of creation, revocation and every changing request; rate limits per address on failures and per token on use. Design in `docs/authentication.md`.
- **Hub backup: one `age`-encrypted file, a portable export, restore offline from the console (#253).** The file holds the database (SQLite `VACUUM INTO`, PostgreSQL exported table by table through the hub's own connection, in one format for both so #124 can reuse it), `secret.key`, `pki/` and a manifest; the metrics tables and the root-owned `config.yaml` and `regulus.env` are left out by default. It is encrypted with a passphrase using `filippo.io/age` (no home-made cryptography, no plain option). Scheduled backups and a `pre-update` backup go to `data_dir/backups/`, which also gives PostgreSQL a rollback (#247). Restore runs with the hub stopped, verifies before it writes, migrates an older backup forward and refuses a newer one; agents enrolled after the backup must enroll again. Dashboard restore comes after the console one. Design in `docs/backup.md`.
- **The hub has no log file; the Logs tab says where to read it without journald (#375).** The hub writes its log to standard error and leaves it to the supervisor (journald under systemd, `docker logs`, the terminal). A `log.file` setting would need a path, permissions for a file that can hold request details, rotation and a place in the package's purge, to serve a few installs that are not the supported platform. When `journalctl` is not on the machine the console's Logs tab (`journalLogs`, `journalFollow` return `console.ErrNoJournal`) shows a translated note instead of the raw error. Revisit if a supported platform ever has no journald.
- **What the hub names by an id is translated in the dashboard (#125).** The permissions, the three built-in roles and the events of the audit log come from the hub as English text, but each has a stable id, so the dashboard shows them from its catalogs (`users.perm.<id>`, `users.roleDesc.<name>`, `users.event.<event>`, `dashboard/src/hubTexts.ts`). An id without a text, from a newer hub, shows the hub's text (an event: its id with spaces), so a hub can be ahead of the dashboard. A role made by an administrator keeps its own words. A new permission, built-in role or audit event adds its line to `users.en.ts` and `users.it.ts`. **Still English** and not covered: see the #368 entry below.
- **The hub's other answers carry a code and arguments (#354).** Input errors (username, password, role, policy), the fleet's name and lifetime errors, the update settings and every update, rollout and agent-listener refusal now answer `{error, code, args}`; the dashboard shows `hub.error.<code>` with `args` as its parameters (`{min}`, `{max}`, `{detail}`), so a text such as "the new password must be 12 to 128 characters" follows the page's language. `update_upstream` and `listener_blocked` end with the hub's English reason as `{detail}`. An error carries its own code through two methods, `Code()` and `Args()` (`auth.inputError`, `fleet.NameError`, update's `settingsError`), which `writeFail` and `writeJSONErr` read, so a new validation adds one line at the place that raises it. `TestEveryErrorCodeHasAText` fails when a code of `auth.ErrorCodes()` or of the hub has no text in either catalog or is missing from `HUB_ERROR_CODES` in `api.ts`; `TestErrorCodesInSourceAreListed` fails when a handler writes a code that is not in the list. 400s of the metrics endpoints (`since`, `step`, `limit`: query parameters a script sends, never the dashboard) stay plain English.
- **The `detail` of an audit entry, and the messages of the helper and of a rollout, carry a code and arguments (#368, was #354 parts 1 and 3).** `audit_log` has two columns, `detail_code` and `detail_args` (migration 0015 on both databases, add-only, empty by default), next to the English `detail`, which is kept. `GET /api/audit` returns `code` and `args` when the entry has them. ## Plugins: manifest and runtime (#19)

Choices made while writing the runtime, so they are not rediscovered:

- **Processes and gRPC on a Unix socket**, as #19 and the tech stack decided. Not the Go `plugin` package (same address space, a crash is the host's crash, exact build match needed) and not WebAssembly (no access to the system, which plugins such as Docker need).
- **The plugin serves, the host connects.** The host names the socket path (`REGULUS_PLUGIN_SOCKET`) in a directory of its own, mode 0700, so no other user can reach the socket, and a plugin can be written in any language with a gRPC server. The host checks the plugin's identity (`Describe`) against the manifest before anything else.
- **The contract is two calls** (`Describe`, `Health`). What a plugin can do is a separate design step (open question 1 in [plugins](plugins/README.md)), not invented here.
- **Restart rules** like systemd's: exponential pause from 1 s to 1 min, reset after a minute of running, and **failed for good** after more than 5 stops in 10 minutes, until the agent restarts. A broken plugin then costs nothing more.
- **Process group per plugin**, `SIGTERM` then `SIGKILL` after 10 s, and the group is killed also when the plugin exits by itself: a plugin cannot leave processes behind.
- **Clean environment**: a plugin gets only the variables it needs, never the agent's (which may hold settings or, on the hub, the database password).
- **The manifest is strict** (unknown keys refused), like the configuration file, and `<X.Y.Z` in `requires` also leaves out the pre-releases of X.Y.Z, unlike plain SemVer.
- **Directory = id, links refused** for plugin directories, and a command that leads outside its plugin directory after following links is refused.
- **Agent first.** The supervisor was first wired into `regulus agent` (`plugins_dir`, off by default); the hub followed in #262 (below).
- **Not done, on purpose:** signatures, installation, enforcement of permissions, a user per plugin. Until #20, the plugins directory must be writable by root only: who can write it decides what runs.

## Plugins on the hub and their state (#262)

- **The hub runs its plugins like an agent does.** `plugins_dir` (`--plugins-dir`, `REGULUS_PLUGINS_DIR`), off by default, read at start, also settable with `regulus config set`. The supervisor (role `hub`) starts in `Hub.Serve` beside the HTTP and agent servers and is stopped before `Serve` returns. Sockets in `<data_dir>/plugins-run`, plugin data in `<data_dir>/plugins-data/<id>`.
- **The database password stays out.** The hub's environment holds `REGULUS_DATABASE_PASSWORD`; the supervisor builds each plugin's environment from nothing (it never copies `os.Environ`), and a test runs a plugin on a hub whose environment holds the password and checks what the plugin saw.
- **Agents report their plugins with their metrics**, not in a new message: `MetricsReport.plugins` and `plugins_enabled` (fields 7 and 8), added to protocol 1 without raising `protocol.Version`, because an older hub ignores unknown fields and an older agent sends none (which reads as "no plugins directory"). The hub keeps the last list with the agent and removes it from the stored report, so it does not fill the hour of metrics history. Lists and texts are cut like the rest of a report (64 entries, 256 bytes).
- **`GET /api/plugins` needs `servers.read`**: the state of what runs on the servers is read like the servers themselves, by every role. It says nothing a viewer could use to change anything; the plugins' errors are messages for an administrator (exit status, health message), not secrets.
- **One JSON shape for the hub and for agents** (`id`, `version`, `state`, `restarts`, `last_error`, `since`); the process id is not sent.
- **The console** shows the hub's plugins on the Status tab and in `regulus status`, only when the hub has a plugins directory, so nothing changes for a hub without one. The agents' plugins are in the dashboard only.
- **Done later (#319):** see the next section.

## Invalid plugins, the Health check and live plugin changes (#319)

- **An invalid plugin directory is a plugin in the state `invalid`**, not a new list: the supervisor lists every directory `Discover` refuses (no or invalid `plugin.yaml`, a name that is not the id, a symbolic link) as `Status{ID: <directory name>, State: "invalid", LastError: <why>}`, with an empty version. So the hub's API, the console and the agents' reports carry it with no new field: an agent sends it as one more `PluginStatus` (only the comment of `state` changed in `agent.proto`), and an older hub shows the unknown state as it is, as the field always said. A directory name is unique in the plugins directory and a valid plugin's id is its directory name, so the two cannot collide. Its manifest cannot say which role it is for, so the hub and an agent that read the same directory both list it. **Rejected:** a separate `invalid` list in `GET /api/plugins` (it would need a new protocol field for agents, and a second table on the page for one row).
- **The console's Health tab has a `plugins` check** while the hub runs with a plugins directory: `warn` when a plugin is `failed`, `incompatible` or `invalid` (each named with its state) or when the directory cannot be read, `info` when it holds none, `ok` otherwise. `starting` and `restarting` do not warn: they are the supervisor at work, and a plugin that keeps failing ends `failed` within minutes.
- **Plugin changes go on `/api/stream` as a signal, not as state.** `plugins.changed` has `source` (`hub`, or `agent` with the agent's `id`) and nothing else; the dashboard reads `GET /api/plugins` again. The hub's supervisor calls `OnChange` when a plugin's state, restart count or last error changes; for an agent, the hub compares each report's list with the last one and pushes only a difference (every metrics interval would otherwise be an event). Sending the state itself was rejected: the API joins agent names from the registry and applies its permission and limits, and duplicating that in the stream would be a second shape to keep in step. The page also reads again after a `snapshot` (a reconnection may have missed events) and when an agent connects or disconnects, and waits 250 ms after a change so a burst is read once. It no longer polls; while the stream is down it shows the last state it read, like the other live views.

## Managers, backends and apps (epic #286, proposed)

Agreed in conversation on 2026-11-19. **Proposed**: the names and the direction are decided, the design of each part is in the issues of #286. Nothing is implemented. The full page is [managers-and-apps.md](managers-and-apps.md).

- **Four words, four meanings.** *Plugin* (code that extends Regulus, unchanged), *manager* (a function of a server Regulus manages), *backend* (the real tool behind a manager), *app* (third-party software in containers). **Rejected words:** *extension* and *add-on* (a second name for plugin), *snippet* (no feature needs it).
- **Manager, not capability.** *Capability* is already in the glossary for what a node type does (#104, #160, #169). One word with two meanings would make "does this node have the firewall capability?" ambiguous.
- **Use existing tools.** Regulus does not write its own RAID, firewall, container runtime or VPN. One **active backend per manager per server**. The firewall is the example: nftables is the kernel layer and ufw and firewalld sit on top of it, so Regulus detects the one the distribution uses instead of offering four equal choices; iptables is not supported. LVM is not an alternative to mdadm (arrays and logical volumes are different layers), so storage and volumes is a separate manager (#293) from RAID (#285).
- **Apps run in containers**, with their data in a declared volume. **Rejected:** installing the software natively in a dedicated volume as a service. It would need an installation, update and cleanup method per program that Regulus would have to know. The container runtime is a backend (Docker or Podman, chosen by the administrator), not a hard-coded choice; the common format is the Compose specification. Kubernetes is out of scope for now. This answers the first item of #113 in direction; the details are #289.
- **Apps are not plugins.** They need no gRPC and no Regulus API. An app that needs something from the host (an open port, a VPN) asks the matching manager and never changes the host itself.
- **Docker was described as a plugin** (the "plugins such as Docker" remark under *Plugins: manifest and runtime* above). With this vocabulary Docker is a **backend** of the container manager; whether the code that drives it is built in or a plugin is open (#287).
- **Milestones.** The model (#287), the apps (#288), the container manager (#289) and the three managers the maintainer named (firewall #290, VPN #291, wake #292) are in **M6**: they define how plugins are used and need #261 first. The other managers (#293 to #300) and the first apps (#301) have no milestone yet.
- **Not decided:** built in or plugin for the part that changes state; how privileged actions work (#60); which guards each dangerous operation needs; observe or manage per manager (RAID proposes *observe first*, #285); whether a node type enables managers by default.

## Changing a node's type, and guided installation (#164, #165, proposed)

Written on 2026-11-19. **Proposed**: waiting for the maintainer's agreement. Nothing is implemented. The full page is [node-type-changes.md](node-type-changes.md); the prototype is `design-drafts/node-types-v2.html`.

- **One operation, three front ends.** The hub has one operation, *set a node's assignment* (preset plus per-node overrides, as in `internal/capability`). The dashboard, the console and `regulus server type` are front ends to it. The hub also says, for each target type, whether the change is possible and why not (a closed list of reason codes with the command that fixes it), so the three cannot disagree. **Rejected:** working the rules out in the dashboard (they would drift from the CLI).
- **A new permission, `servers.assign`**, admin only by default. **Rejected:** reusing `servers.manage` (given to `operator`): making a server public is a change in exposure, not housekeeping. Opening a listener and promoting a hub also ask for the password again (#279, done for the agent listener; to be applied to these when they exist).
- **The second key is `allow` in `/etc/regulus/agent.yaml`**: empty by default, only capabilities that need consent (`relay`, `notifications`, `authentication`), set with `install.sh --allow`, `regulus agent allow`, the node's console, or by hand, always as root on the node. **The hub can never change it**: no message carries it from the hub, and the agent process cannot write the file (`0640 root:regulus`). The node reports the list, and the report can only narrow what it does. The effective set is *assigned ∩ allowed*, enforced by the hub and again by the node.
- **Backup storage needs a place, not consent:** `backup-storage` opens no port, but it cannot be applied until the node has set `backup_dir` with enough free space.
- **Role or capability.** Changing between compute, backup, gateway and development is a capability change on the role `agent`. Redundant hub is a role transition through #105. The active hub is never changed by this operation (#109).
- **While connected:** a new `Assign` command carries the full effective list (protocol version bump, N / N-1), `Welcome` carries the current assignment, and there is an assignment version per node. An offline node, or one on an older protocol, keeps the change as *pending*.
- **Undoing a type moves no data.** A gateway stops at once. A backup node stops accepting new backups but keeps what it has, read-only, until the administrator moves (#171) or deletes it. Workloads block a change to a type without `workloads`.
- **Guided installation: one source.** One YAML file per type, embedded in the binary (`internal/guide/steps/<type>.yaml`), feeds the dashboard wizard, the console, generated documentation (checked by CI) and a JSON export for the configurator (#167). Placeholders come from a closed list with no template logic. Texts are in English and Italian inside the file; **commands are never translated**. Checks come from a closed list implemented in Go. **Rejected:** keys into the dashboard's catalogs (the console and the configurator could not read them).
- **Checking each step:** *auto* (the hub checks, and checks again while the wizard is open), *manual* (the administrator confirms; shown as "confirmed by you, not checked"), or *partly*. "Reachable from outside" is proved only from the hub's network; the internet test stays manual. **Rejected:** an external probe service (a third party would learn the group's addresses).
- **The type travels with the enrollment token**: the wizard stores the intended preset with the token and the hub assigns it at enrollment. The node still applies only what `allow` permits.
- **Secrets:** token rules unchanged. The token is shown once and never appears in the docs, the configurator, URLs, logs, audit details or the wizard's saved record.
- **Not decided:** the permission name and whether `operator` gets the light changes; whether `accept_promotion` moves into `allow`; a redundant hub that also carries agent capabilities (proposed no); leaving the development type; the minimum resources per type (to measure).

## Capabilities: consent is part of the model (audit issue #317)

The draft `internal/capability` turned `relay` and `inbound-listener` on in the gateway preset, while [node-types.md](node-types.md) called them opt-in, and `Has(Relay)` was true without the node's agreement: code written later against it could open a public listener on a node that never agreed. Choices (the package is still a draft that nothing calls):

- **Consent is modelled, not left to callers.** `Resolve(preset, override, allowed)` takes the node's `allow` list (as the node reported it) and returns only the effective set: a capability that needs consent is in it only when assigned **and** allowed; otherwise it is in `Withheld` ("assigned, not allowed by the node"). `Defaults(p)` is `Resolve` with no override and an empty list, so no preset reports an exposure capability by default. **Rejected:** only removing relay from the gateway defaults: it would agree with the table but `Has` would still mean "the hub said so", and the next exposure capability would have the same hole.
- **The gateway preset still assigns `relay` and `inbound-listener`**: choosing the type is the hub's key, as in [node-type-changes.md](node-type-changes.md) (`--allow gateway` writes `relay`); the table in node-types.md now says `consent` for them and keeps `opt-in` (administrator **and** node) for `notifications` and `authentication`.
- **The listener follows the capabilities**: `inbound-listener` is effective only while a consent-needing capability is effective (`PermissionNeedsConsent`), because `allow` names capabilities only.
- **Unknown names are refused** in an override and in the allow list (`ErrUnknown`), and the allow list may hold only capabilities that need consent (`ErrNoConsentNeeded`), as node-type-changes.md says for the file.

## Web terminal and file browser (#236, #237, proposed)

Proposed on 2026-11-19, **waiting for the maintainer's agreement**; nothing is implemented. The full design, with the threat model, is [node-access.md](node-access.md); the prototype is `design-drafts/node-access-v2.html`.

- **One answer for both.** The terminal and the file browser share one transport, one root helper and one answer to "as which user", under the name **node access** (not related to Regulus Access).
- **As which user: a local account of the node, authenticated by the node (PAM).** A new socket-activated root unit, the **session helper**, checks the account against a root-owned list on the node (`/etc/regulus/node-access.yaml`, empty by default, `root` always refused), runs PAM with the prompts relayed to the browser, opens a real login session and drops to that account before starting the shell or the file worker. `sudo` inside follows the node's own rules, so Regulus never grants root. **Rejected:** a shell as the agent's own sandboxed user (safe and almost useless); an SSH client to the node's `sshd` (needs `sshd` everywhere and keys or passwords handled by the hub; possible later as a second backend); a root shell on a hub grant (a hub compromise would be root everywhere).
- **Core, off by default on both sides ("two keys").** In the single binary; the hub grants the capability `terminal` or `files` per node (audited, step-up) **and** the node opts in locally (`install.sh --allow terminal,files`, `regulus node-access enable …`). The helper units ship disabled, so a node that never opts in cannot be reached even by a compromised hub. **Rejected:** a separate package (one binary, #227) and a plugin for now (the plugin runtime cannot host a root helper and isolation, #267, is not designed); #68 is to be updated.
- **Explicit permissions.** `terminal.open`, `files.read`, `files.write`, `files.delete`, `files.chmod`, `sessions.manage` are not covered by a role with "every permission", so the built-in `admin` does not get them by upgrading; two-factor must be on, and every new session asks for the password and the code (#279).
- **Files only beneath roots listed on the node**, each `ro` or `rw`, resolved with `openat2` (`RESOLVE_BENEATH`, no magic links, no mount crossing) and fd-relative operations; refused on kernels without `openat2` (RHEL 8). No trash; recursive delete names the node and the path.
- **Each session has its own gRPC stream** on the agent's existing mTLS connection (agent protocol 2), so transfers never delay heartbeats; HTTP/2 flow control is the backpressure. Node access is refused over plain HTTP except from loopback.
- **Recorded:** every session and every file change in the audit log, never content; the node keeps its own login records through PAM. **Not recorded:** session contents (no recording in the first version).
- **Residual risk accepted:** after a hub compromise, local passwords typed into the dashboard can be captured; mitigations are on the node (dedicated accounts, PAM TOTP, short lists, the node key off).
- **Milestone:** M4, after this design, #169/#170 and #279 are agreed.
- **Not decided:** two-factor required versus following the global policy; whether listings are audited; xterm.js under the hub's CSP (it injects inline styles); SELinux on RHEL; per-node scoping of user permissions (waits for node groups); detach and reattach.

## Network visibility: open ports and the traffic map (#282, #283, proposed)

**Proposed**, awaiting the maintainer's agreement; nothing is implemented and the kernel behaviour it relies on has not been checked on a real machine. The full page is [network-visibility.md](network-visibility.md); the prototype is `design-drafts/network-v2.html`.

- **Sockets, not packets.** The agent reads the kernel's socket tables through `sock_diag` netlink (what `ss` uses), with `/proc/net/{tcp,tcp6,udp,udp6}` as a fallback, unprivileged. **Rejected:** packet capture (needs `CAP_NET_RAW`, costly, sees content), eBPF (needs `CAP_BPF`/`CAP_PERFMON` and BTF; revisit as a privileged tier), conntrack on every server (needs `CAP_NET_ADMIN`; it is the right source on a firewall node, #284), and interface counters as proof of "in use" (they stay the total).
- **Owner without root:** the socket's user, and its systemd unit or container from the socket's cgroup id. The exact process of another user's socket comes only from one fixed, opt-in root-helper operation (inode → pid, name, executable, unit; no command lines), as a privileged action of #60. **Rejected:** `CAP_SYS_PTRACE` for the agent (root in practice), `sudo ss -p` (blocked by `NoNewPrivileges`), running the agent as root (#46). The units need `AF_NETLINK` in `RestrictAddressFamilies`.
- **Labelling honestly.** Regulus's own traffic (agent connection, update download, replication) is counted exactly inside Regulus and labelled by kind; everything else is *other* with the owner Regulus could read, and what no socket explains is shown as *unattributed*. A protocol is never inferred from a port number.
- **One collector.** A single network-state collector in the agent; the inventory (#62) shows its listeners instead of collecting ports again.
- **Stored on the hub:** current listeners plus a change log (appeared, gone, owner or exposure changed, a baseline row for a new agent, flapping collapsed), not a time series. Traffic is summarised per destination per interval: 5-minute buckets for 48 hours, hourly for 30 days, capped per agent and under a global byte budget (#244). Numbers are proposals. **Rejected:** keeping raw connections.
- **Protocol:** add-only. New `AgentMessage` payloads (`NetworkState`, `TrafficReport`), `Welcome.network` saying what the hub wants, a `RefreshNetwork` command; sent only when `Welcome` asks, so no `protocol.Version` bump and the update contract is untouched.
- **Privacy:** destinations are addresses, ports, owners and bytes, never content, URLs, DNS queries or SNI. Destination collection is **off by default per node**; the hub turns it on and the node can refuse locally (deny wins). Reverse DNS by the hub is opt-in and labelled "reverse name".
- **Permissions:** `ports.read`, `traffic.read`, `destinations.read`, `traffic.configure`, all admin-only by default; viewing and switching collection are audited (coalesced per user and hour).
- **Expected ports** come only from declared sources: Regulus's own listeners, node type presets (#169), app manifests (#288), managers (#290), plus an administrator's audited acknowledgement. **Rejected:** a built-in list of "usual" ports.
- **Read-only.** Opening and closing ports belongs to the firewall manager (#290) and the firewall node (#284). The ports page makes the rule of #197 visible on every server; it does not replace the default.
- **Not decided:** whether `ports.read` should be `inventory.read`; whether destinations default on for some node types; replication of this data (#106); alerts on an unexpected port need an alerting design that does not exist.

## install.sh requires a valid signature, with the exact tag identity (#208)

- **Required by default.** `install.sh` downloads `checksums.txt.sigstore.json` and stops when it is missing or invalid. The old behaviour (a warning and success when cosign was absent, which is the normal case on a fresh Ubuntu) made the signature optional exactly where it matters: `checksums.txt` and the `.deb` come from the same origin, so the checksum alone proves nothing about who built them. The opt-out is explicit: `--allow-unsigned` or `REGULUS_ALLOW_UNSIGNED=1`, which says so loudly. `--require-signature` stays accepted and does nothing, so old commands keep working.
- **The exact identity.** Both ways of checking use `release.yml@refs/tags/v<version>`, as the hub does, not `release.yml@.*` (any ref, any branch): a signature a workflow run made on another ref is refused. The documents and `.goreleaser.yaml` show the same.
- **Who checks.** cosign if it is installed; otherwise `regulus verify-release --tag vX checksums.txt bundle`, new, which runs the same `SigstoreVerifier` as the hub and which the installer takes out of the package without installing it (`dpkg-deb -x`, no root needed to look). **The honest limit:** without cosign the package verifies itself. A hijacked origin could ship a package whose `verify-release` says yes; the check still stops a mistake, a stale mirror and a signature of another tag. For a check that does not depend on the origin, use cosign or the manual steps in `docs/releases.md`. The first install trusts GitHub and TLS in every case.
- **Transport.** `curl --proto '=https' --tlsv1.2` (`wget --https-only`) for every download, including the release lookup; `--base-url` must be `https://` unless `--insecure-base-url` is given for a test server.
- **Tested** with stubs in `scripts/test-install.sh` (missing, invalid and wrong-tag signatures, through cosign and through the package) and in Go (`cmd/regulus/verify_release_test.go`, the identity itself in `internal/update/signature_test.go`). **Not verified** on a real Ubuntu with a real signed release (`[Test]` issue).

## The release workflow: build apart from signing (#206)

- **Two jobs, one workflow file.** The signing identity is `release.yml@refs/tags/<tag>`, so both jobs stay in that file. **build** runs everything that installs or runs third-party code (`npm ci`, `go build`, GoReleaser, syft) with `contents: read` and **no `id-token`**: nothing it runs can ask Sigstore for a certificate. **publish** has `contents: write` and `id-token: write`, installs nothing but cosign, builds nothing, checks every file against `checksums.txt` (and that nothing outside it is published), signs `checksums.txt` and creates the release with `gh release create`. The workflow-level permissions are empty; each job asks for what it needs.
- **What this protects, and what it does not.** A compromised npm package, action or install script in the build job can no longer read the OIDC token and sign something of its own choosing. It **can still change what the build produces** (the dashboard bundle, the binary), and that is then signed. Making the build itself trustworthy is a different problem (reproducible builds and provenance, #215); the split only keeps the signing key out of its reach. The transfer between the jobs is checked by `upload-artifact`/`download-artifact` (digest) and by `sha256sum --check --strict checksums.txt`.
- **Why not `goreleaser publish`.** It cannot sign: signing is a step of GoReleaser's release pipeline, not of `publish`. So the build job runs `release --skip=publish,sign,announce` and the publish job signs with cosign (the same flags as `.goreleaser.yaml`: `--new-bundle-format`, bundle `checksums.txt.sigstore.json`) and creates the release itself. The release notes (install command, then the changelog) are written by the workflow; the `release` and `signs` sections of `.goreleaser.yaml` are no longer used by the workflow and stay as documentation and for `goreleaser check`.
- **Versions pinned:** GoReleaser v2.12.0 (also in `ci.yml`'s check), cosign v2.6.1, syft v1.57.2. `npm ci --ignore-scripts` builds the dashboard (`make dashboard`); checked that the build works without install scripts.
- **Every action is pinned to a commit (#361, was #206).** `scripts/pin-actions.sh` resolved each tag with `git ls-remote` (the annotated tag's commit wins) and kept the tag as a comment, which Dependabot understands and updates together with the SHA. The `go` job of `ci.yml` runs `scripts/pin-actions.sh --check`, so a `uses:` that is not a 40-character SHA fails the build. A pinned SHA protects against a moved tag, not against a malicious commit that Dependabot later proposes: review those updates.
- **First run found a bug (v0.3.0-alpha.1, #364).** The publish job has no checkout (by design), so `gh release create` failed with "not a git repository"; build, index and signing had passed. Fix: `--repo "$GITHUB_REPOSITORY"`. The workflow that runs is the one at the tag, so the failed tag could not be re-run: it was deleted and made again on the fixed commit (the release did not exist, no hub could have seen it). `publish-index` already named the repository.
- **Not verified:** the whole workflow runs only on GitHub Actions on a tag. GoReleaser was run here up to the `dist/` directory and the checks of the publish job were run on it; the sign and `gh release create` steps were not. The first release made with it needs a `[Test]` (publish an alpha, check the signature with `regulus verify-release` and the exact identity).

## The embedded Sigstore root: not harmless when stale (#214, partly done)

- **The old comment was wrong.** `signature.go` said a stale snapshot "only makes verification fail, never pass". After a key revocation or rotation a stale root keeps trusting keys and authorities Sigstore has retired, so a signature the live root refuses could pass. Corrected in the code.
- **Done:** (1) the fallback is no longer silent: `PublicTrustReporting` calls back when the source changes; the hub logs a warning once, the Updates page shows the reason (`trust_fallback`, English and Italian), the agent logs it; the embedded snapshot is retried every hour instead of every 12 (`trustRetryEmbedded`), so the warning clears soon after the network is back. (2) A weekly workflow runs `cmd/refresh-trusted-root` (the TUF fetch, written in a stable layout and compared by data, not by bytes) and opens a pull request when the root changed; a pull request made with the workflow's own token does not start CI, which the workflow says. The snapshot in the repository was compared with the live root when this was written: identical.
- **Not done: the hub serving its current root to agents.** An agent that needs no internet today waits for the TUF fetch (up to 20 s) the first time it verifies and then uses its snapshot, whose cache never updates. The fix is a new RPC (or a field of the update offer) that carries the hub's root over the mTLS channel, which touches `proto/` and `docs/versioning.md`; it is its own issue, so #214 stays open for it.
- The fallback still applies when TUF is blocked by an attacker: it is shown now, not prevented. Refusing to verify with a snapshot older than some age is possible and was not chosen: a hub with no internet would then never update at all.

## Who can make a trusted release (#207, partly done)

- **The risk.** Hubs and agents install, as root, anything signed by `release.yml@refs/tags/<tag>`. The workflow that runs is the file at the tagged commit. So "who can push a `v*` tag" (or tag a commit of a branch whose `release.yml` was changed) equals "root on the fleet". The checks for "on main" and "CI passed" were only in `publish-release.yml`, which a hand-pushed tag skips.
- **Done in the repository:** `release.yml` now fails before it builds unless the tagged commit is an ancestor of `origin/main` and CI succeeded on that exact commit; the publish job runs in the `release` environment. These checks stop a mistake and an unreviewed commit. They do **not** stop someone who can push a tag, because that person can also remove the checks from the workflow at that tag.
- **Not done, because it is a repository setting and not a file** (a maintainer does it; it cannot be checked from here): a tag ruleset (only maintainers create `v*`, nobody moves or deletes one), required reviewers and a `v*`-only deployment rule on the `release` environment, and two-factor authentication or a hardware key for those accounts. Described in `docs/releases.md`; a `[Test]` issue asks for the settings and for the demonstration the issue wants (a tag on a commit that is not on main, or without green CI, produces no release). The issue stays open until then.
- **Kept the push-tag trigger**, because the documents say a tag pushed by hand works and the new checks make it safe against a mistake; dropping it would not remove the real risk (the ruleset does).

## Load test of the hub (#234, partly done)

- **A repeatable run exists** (`TestHubUnderLoad`, `docs/development.md`): N simulated agents, M polling dashboards, CPU, latency and the metrics history, with the hardware and one result written down. At 200 agents and 20 dashboards the hub used about 1.4% of one CPU at the real report rate and 4.4% at ten times it, and the two API calls answered in single-digit milliseconds at p95.
- **A finding about the measurement, not the hub:** the in-process transport (`internal/inproc`, 1 MiB buffer per direction per connection) makes memory per agent look like 2 MiB. That is the transport of the built-in agent, which only one agent uses; it says nothing about the 200 remote connections, so the test reports the hub's own estimate of the history (about 4 KiB per agent for 30 reports) and says why the heap is not the hub's share.
- **Not done, and left open on #234:** the same run over real TLS connections, the WebSocket fan-out, the SQLite and PostgreSQL write paths under many dashboards and users, and the browser profile with 50 agents. The documents do not claim a supported scale beyond "this run".
