After the login the dashboard shows a **sidebar** on the left with the sections **Dashboard** and **Servers** (Overview), **Users** (for those who may manage users or roles or read the audit log) and **Updates** (with `core.update`) (Administration), and at the bottom an account card that leads to your **Account** page (change password, two-factor, your sessions, appearance and language), **Sign out** and a button that collapses the sidebar to icons. Below 52rem the sidebar is a drawer opened by the menu button. The **top bar** shows the page title, the state of the live updates (Live, Connecting, Reconnecting), the theme (System, Light, Dark) and the language (browser language, English, Italian); both choices are saved in the browser and are also on the Account page. The **Dashboard** page is a grid of widgets: **Customize** unlocks dragging and resizing, **Add widget** picks from the registered widgets, and **Reset to default** restores the initial layout. Below 1024 px the grid is a stack of one (below 40rem) or two columns in the saved order, and while customizing each widget has **Move up** and **Move down** instead of dragging. The layout is saved per user through `/api/layout` (with debouncing, and flushed when leaving the page). Widgets are registered in `dashboard/src/widgets/` with `registerWidget` (id, title, default size, component); a widget that crashes only breaks its own frame, an error outside the widgets shows an error screen with a reload button instead of a blank page, and a layout that refers to an unknown widget (for example from a removed plugin) shows a placeholder that can be removed.

**Look and shared pieces** (#91). The visual direction is the "machine room" of `design-drafts/machine-room-v2.html`: concrete and graphite colours, one safety-yellow signal for the brand and for primary actions, Archivo and IBM Plex Mono (bundled, the hub's CSP allows no outside fonts). Colours are tokens on `:root` in `dashboard/src/styles.css`, redefined for dark mode. Status is always a badge with a word, never colour alone. Tables become one card per row below 48rem and their row actions move into an **Actions** menu (`RowActions` in `dashboard/src/ui.tsx`); destructive actions ask in place (`ConfirmButton`), not with the browser's `confirm`; **Copy** buttons say how to copy by hand where the browser cannot (a hub on plain HTTP has no clipboard API). The isometric room of the draft is not built yet: it needs the physical place of each node, which Regulus does not know (see `design-drafts/README.md`).

After the login the dashboard shows a header with the sections **Dashboard**, **Servers**, (for those who may manage users or roles or read the audit log) **Users** and (with `core.update`) **Updates**, and a link to your **Account** page (change password, your sessions). The **Dashboard** page is a grid of widgets: **Customize** unlocks dragging and resizing, **Add widget** picks from the registered widgets, and **Reset to default** restores the initial layout. The layout is saved per user through `/api/layout` (with debouncing, and flushed when leaving the page). Widgets are registered in `dashboard/src/widgets/` with `registerWidget` (id, title, default size, component); a widget that crashes only breaks its own frame, and a layout that refers to an unknown widget (for example from a removed plugin) shows a placeholder that can be removed.

The base installation ships these widgets, fed live by the hub (the dashboard follows `/api/stream` and reconnects by itself if the connection drops): **System** (host, OS, kernel, memory, load, uptime), **CPU** and **Memory** (current value plus a chart of the last 10 minutes), **Network** (received and sent rate, in total and per interface; the total leaves out bridges, container and VM ports, tunnels and VLANs, whose bytes are already counted on the physical interface, and the table still lists them all), **Disk usage** (one bar per mounted filesystem), **Uptime**, and **Servers**. The first five (without Uptime) are in the default layout. When several agents are connected, each widget has a selector and remembers the choice; by default it shows the hub's built-in agent.

The **Servers** page lists every enrolled server, online or not, with its system, agent version, status (online, stale, offline, revoked) and last contact, and a count by status when there are several. Users see each session as "Chrome 156 on Windows", and the Add a server form lets you choose how long the token is valid (15 minutes, 1 hour, 24 hours or 7 days). A row opens the page of that server: its facts and the System, CPU, Memory, Network and Disk usage widgets bound to it. Those with `servers.manage` rename or revoke a server there and add new ones with **Add a server**. An offline server shows when it was last seen; a revoked one cannot connect again.
