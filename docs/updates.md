# Updates

The hub looks for new releases of Regulus, keeps the newest one downloaded and checked, and can install it on its own server from the dashboard, with a rollback. The servers you manage (the agents) are updated from the hub too.

- **Where from:** the [GitHub Releases](https://github.com/Stellatinus/Regulus/releases) of this repository, read without a token. The hub asks every six hours (a little later after a restart, and at most once a minute from the dashboard), with conditional requests so it stays well under GitHub's limit for anonymous use. Only the first request after a change of the list costs anything. The list is read 100 releases a page, and further pages only while none of the releases read so far is a stable release of the core (plugin releases share this repository and could otherwise push the newest stable release out of the first page), at most 5 pages. **If the hub cannot get an answer for more than three days** (or never got one), the Updates page warns that it may not know about a release, a security fix included, and shows when the last check succeeded (`succeeded_at`, `check_stale` in `GET /api/updates`). A hub that runs without its local status socket (a `data_dir` path too long for a Unix socket, or a socket that cannot be made) is still updated, through `<data_dir>/running.json`; `GET /api/updates` then carries `status_socket`, the reason, and the Updates page says that `regulus status` shows no live data and that an update from a release older than the fix of #312 rolls back on such a hub. A development build (`dev`, or one made after a tag with `git describe`) never asks by itself and is never told it is behind.
- **Channel:** `stable` offers releases only; `beta` also offers betas and release candidates (`v0.3.0-beta.1`, `v0.3.0-rc.1`); `alpha` offers every release, alphas included (`v0.3.0-alpha.1`, and any other pre-release). Each channel takes whichever offered release is newest, so it moves to the beta or the release when one comes out. A hub starts on the channel of the version it runs. Versions are compared as SemVer, so a hub never "updates" to something older.
- **Mode**, chosen in the dashboard (**Updates**, needs the `core.update` permission, which `admin` has and `operator` does not): `manual` only tells you; `download` also downloads the archive of this platform into `<data_dir>/updates/` and checks it, then waits for you to press **Install** (the default, so a new hub never installs anything without an administrator); `automatic` also installs it by itself, but only inside a maintenance window you set (two times such as 03:00 and 05:00 in the server's time zone, possibly across midnight), and never tries again a version that had to be rolled back. Every change of settings, every download and every installation is in the audit log.
- **What "checked" means:** first the signature of `checksums.txt`, then the archive. The release workflow signs `checksums.txt` with Sigstore (keyless, `checksums.txt.sigstore.json`); the hub verifies that bundle in-process, with no `cosign` needed: the certificate must name the release workflow of this repository **at the tag of the release**, issued by GitHub Actions, with a transparency log entry and a certificate timestamp. Only then is the archive downloaded and its SHA-256 compared with the list; a mismatch deletes it. A release with a missing or invalid signature is never kept. The Sigstore trusted root is fetched from Sigstore's TUF repository and cached in `<data_dir>/tuf` (a key rotation reaches the hub by itself); if that cannot be reached, a snapshot built into the binary is used. **That snapshot is not harmless when it is old:** it keeps trusting keys Sigstore has since revoked. So its use is logged (hub and agent), the hub asks again every hour while it is in use, and the Updates page says why (`trust_fallback` in `GET /api/updates`). A scheduled workflow (`.github/workflows/trusted-root.yml`, every Monday) opens a pull request when Sigstore's root changes, using `cmd/refresh-trusted-root`.
- **Installing, and why no `sudo`:** the hub runs as the unprivileged user `regulus` and keeps it that way. The package ships `regulus-update.path`, which the installer enables (`install.sh --no-self-update` skips it) together with `updates.apply: true` (`REGULUS_UPDATES_APPLY`). When you press **Install** the hub leaves a request that names a version, nothing else; systemd starts `regulus-update.service` as root, which runs `regulus update-apply`. That helper **trusts nothing the hub's user could have written**: it copies the archive into a directory of its own, verifies the Sigstore signature of `checksums.txt` and the archive against it again, refuses a version that is not newer than the installed one, extracts the executable, checks that it reports the expected version, keeps the current binary in `/var/lib/regulus-update/regulus.previous`, replaces `/usr/bin/regulus` atomically and restarts the hub. It then watches the new hub (the service must be active and report the new version and stay up for 15 seconds, within 90). The version comes from the hub's local status socket (`regulus.sock`); a hub that has no socket (the path of the data directory is longer than the 107 bytes a Unix socket allows, or its file system has none) reports it in `<data_dir>/running.json`, which every hub writes when it starts serving, and the helper reads that file when the socket does not answer. A rollback whose cause is neither names the socket and the file. This works from the version that brought it (#312): the helper that runs is the one of the version installed before the update, so the update from an older version on a hub without a socket still rolls back; if not, the previous binary is put back and restarted, and the result is `rolled_back`. The hub restarts in the middle, so the dashboard is unreachable for a moment; the outcome (`applied`, `rolled_back`, `failed`) appears on the Updates page and in the audit log. Only the executable is replaced: a release that changes the systemd units or the configuration file needs the package (`install.sh`) once. Because dpkg does not know about the replaced file, `dpkg --verify regulus` reports it as changed, and a later `apt` reinstall of the package brings back the version in the package.
- **Updating the servers (agents):** the hub is updated first, then the servers, to the version the hub runs; an agent may be one release series behind (see *Versions*), so there is always a window in which both can run. The **Updates** page lists the connected servers that are behind and updates them a wave at a time (1, 3, 10 or all), stopping at the first failure, with a result per server and an entry in the audit log (`POST /api/updates/rollout`). In the `automatic` mode the hub does it by itself inside the maintenance window, and does not retry a rollout that failed. How it works: the hub makes sure its cache holds the signed release with the archive of each platform in use (amd64 and arm64), downloading what is missing; it sends the agent an `ApplyUpdate` command; the agent fetches `checksums.txt`, its signature and **its own platform's archive** from the hub over its existing mTLS connection (so it needs no internet), checks the signature and the checksum, and leaves a request for the helper of its server (`regulus-agent-update.path`, which the installer enables for the agent role together with `updates: true` in `agent.yaml`; `--no-self-update` skips it). That helper works exactly like the hub's: it checks everything again as root, replaces the binary and restarts the agent. The new agent is healthy when it **connects to the hub again with the new version** (it writes `connected.json` for the helper); if it does not within 90 seconds the previous binary is put back. The hub marks a server `updated` only when it has stayed connected with the new version for 30 seconds (the helper on the server keeps watching the new agent for 15 seconds after it connects and can still roll it back), and `failed` if it connected with the new version and then came back with the old one (rolled back), or if after 10 minutes it is not connected with the new version. A reconnection with the old version before that is not a failure by itself: a network blip can reconnect the old agent before the helper ran. The hub sees every connection, so a new version that is rolled back a few seconds after it connected is not missed. An agent installed before this feature has to be updated once with `install.sh`; the dashboard says so. **A server that was off for a long time** (further behind than the hub serves, for example two release series) is not refused: it connects in an *update-only session*, is listed among the servers to update, and the rollout takes it straight to the hub's version (see [Remote agents](remote-agents.md), "Versions", and [Versioning](versioning.md)). A rollout lasts as long as the hub runs: restarting the hub ends it. The last rollout, server by server, and the version for which a rollout failed are kept in the database (`settings`), so after a restart the page still shows them (a rollout that was running is shown as stopped, and the servers it was waiting for as *result unknown*), and the automatic mode still does not try that version again. A rollout that ends well clears that memory.
- **A local policy on what the helper installs (#215).** A signed release is genuine, but not always one this server should take: a hub on the `alpha` channel, a compromised hub or a mis-click could otherwise push `1.0.0-alpha.1` or a new major version to a stable server, installed as root. The root helper therefore reads **`/etc/regulus/update-policy.yaml`** (a path only root writes; `--policy` changes it) and refuses what it forbids, whoever asked and whatever the dashboard's channel says:

  ```yaml
  max_channel: stable   # stable, beta or alpha: the least cautious channel allowed
  max_major: 1          # the highest major version allowed
  ```

  Both keys are optional and the file is optional: without it nothing is limited, as before. The helper does not install the release and writes a `failed` result that the Updates page shows (`policy_channel`, `policy_major`). A file that is not a regular file, is writable by anyone but its owner, is not owned by root, or does not parse is not ignored: the helper refuses every installation until it is fixed (`policy_unreadable`), because ignoring a policy it cannot read would be having none. The same file serves a hub and an agent on the same machine. The package does not create it, and a purge removes it.
- **Custom `data_dir` and the path units.** `regulus-update.path` and `regulus-agent-update.path` watch `/var/lib/regulus` and `/var/lib/regulus-agent`, where the request is left. With another `data_dir` nothing watches the place the hub writes to, so the **Install** button leaves a request that no one picks up: install from the dashboard only works with the default directories, or after editing the path unit and the `--data-dir` of the service with a drop-in (`systemctl edit regulus-update.path`).
- **What a purge removes.** `apt purge regulus` removes the helper's own state, `/var/lib/regulus-update` (the previous binary and the signature trust cache) and the files a killed update can leave next to the executable (`/usr/bin/.regulus.update`, `/usr/bin/.regulus.rollback`), with the settings in `/etc/regulus`. The data of the hub and the agent is still kept.
- **A signed index of releases, against hidden releases (#263).** A server that answers but leaves new releases out (a mirror or proxy that lies, a compromised account that hides a release) looks like "no new release", and every hub would stay on an old version with no warning. The release workflow therefore publishes **`latest.json`**, signed with the same Sigstore identity as `checksums.txt` (`latest.json.sigstore.json`), as an asset of a release. It names the newest release of each channel and carries `issued_at` and `expires` (21 days after it was issued; a weekly workflow, `refresh-latest.yml`, makes a new one for the newest stable release, so it never runs out while releases are served):

  ```json
  {"tag": "v1.4.0", "issued_at": "2026-11-22T05:17:00Z", "expires": "2026-12-13T05:17:00Z",
   "channels": {"stable": "v1.4.0", "beta": "v1.5.0-beta.2", "alpha": "v1.5.0-alpha.1"}}
  ```

  At every check the hub reads the index of the newest release that carries one and verifies its signature (the identity must be the release workflow **at that tag**, and the file must say it belongs to that tag). It never accepts an index **older than the last one it verified** (a replay), and the Updates page warns (`index_problem` in `GET /api/updates`, with the index it verified in `index`) when: the index has **expired** (`expired`); an older one is offered (`replayed`); it names a release newer than the list of releases holds, on a channel this hub follows (`hidden`, the freeze); the hub verified one before and none is offered now (`missing`); or it could not be fetched or verified (`invalid`, with the reason). A hub that never saw an index and finds none says nothing, because releases made before the index existed carry none. The warning means the hub may not know about a release that exists; it does not stop anything, and a failed index never stops the update that the list of releases offers. What this does **not** do: it cannot tell the hub about a release made **after** the last index and hidden at the same time; that window is at most the 21 days of validity, as with the timestamp of TUF.
- **Turn it off:** set `updates.check: false` (or `REGULUS_UPDATES_CHECK=false`) on a hub that must not contact the internet. Nothing is requested then, and the page says why.
- **API:** `GET /api/updates`, `PUT /api/updates/settings`, `POST /api/updates/check`, `POST /api/updates/download`, `POST /api/updates/apply`, `GET`/`POST /api/updates/rollout` and `POST /api/updates/rollout/stop` (all need `core.update`; see `internal/hub/openapi.yaml`). The download runs in the background; poll `GET /api/updates`.

## After the move of the repository

The repository moved to `Stellatinus/Regulus`. Releases are signed by the repository that publishes them and an installed Regulus accepts only the identity that was current when it was built. A server running **`v0.2.0-alpha.1` or older cannot update itself** to a later release: it refuses the signature (the Updates page says the signature is not valid). Reinstall once with the installer of the new release, which keeps the data and settings of an existing installation:

```sh
curl -fsSLO https://github.com/Stellatinus/Regulus/releases/download/vVERSION/install.sh && sh install.sh --version VERSION
```

Use `--role agent` options as shown on **Servers → Add a server** for a remote agent; an agent that is already enrolled keeps its certificate. From the first release built after the move, updates work from the dashboard as before. See [Design decisions](decisions.md#the-repository-moved-audit-issue-231).

## What the root helper does with a request it cannot use

The directory that holds `request.json` belongs to the hub's unprivileged user, and systemd starts the helper for as long as the file exists. The helper therefore **removes whatever is at that place** (garbage, a file over 64 KiB, a symbolic link, a FIFO, a directory) before it does anything else, never follows a link and never blocks on a FIFO, writes a `failed` result that the Updates page shows ("the update request could not be read … it was removed"), and exits with an error. The path unit stays active, and the next valid request is installed normally. (Before this, an unreadable file was left in place and the helper was started again and again until the path unit gave up, so no later update ran until `systemctl reset-failed regulus-update.path`.) To test it on a real machine see the `[Test]` issue for the update helper under faults.

## If the helper is interrupted

Replacing the executable and checking the new version take a while (the health check holds for up to 90 seconds), and the helper can be cut off in the middle: out of memory, `systemctl stop`, its 20-minute limit, a power cut. What is done about it (`internal/update/pending.go`, `installer.go`):

- **The new executable is on disk before it is renamed into place** (the file and the directory are synced), so a power cut leaves the old executable or the complete new one, never half of one.
- **A marker `pending.json`** in the root-owned state directory (`/var/lib/regulus-update`) says which update is in flight (from, to, the copy of the previous executable, the unit). It is written before the swap and removed when the update ended, applied or rolled back.
- **`regulus update-apply --recover` settles a leftover marker:** if the executable is the new version the service is restarted and watched like in a normal update (healthy: the update stands; otherwise the previous version is put back); if it is anything else (the old version, a missing or damaged file) the previous version is put back from the kept copy. The marker is always removed at the end, so it cannot start the helper again and again. Every run of the helper does this first.
- **systemd runs it after the helper stops, whatever stopped it** (`ExecStopPost=+` in `regulus-update.service` and `regulus-agent-update.service`, `TimeoutStopSec=5min` so a stop does not cut a rollback short). A stop or a time limit that arrives during the health check does not stop the rollback either: it runs with its own time limit.
- **One helper at a time.** Every run takes a lock in the state directory (`/var/lib/regulus-update/lock`, released when the process ends, however it ends), so an update that was asked for and the recovery below never work on the executable together.

## If the power is cut in the middle

A power cut (or a crash of the machine) between the replacement of the executable and the confirmation leaves the marker and nobody to act on it: the helper is not running any more. Two units, enabled by the installer together with the path unit (and by the package on an upgrade when the path unit is enabled), settle it **when the machine starts**. Both do nothing unless `/var/lib/regulus-update/pending.json` exists.

1. **`regulus-update-recover.service`, before Regulus starts** (`Before=regulus.service regulus-agent.service`). It runs `/usr/lib/regulus/update-recover`, a shell script, so that it works **even when `/usr/bin/regulus` cannot run**: in that case the script copies the previous version back from the copy the helper keeps (it tries the copy first, and never follows a link), then hands over to `regulus update-apply --recover --before-start`, which only does what needs no running service and asks systemd for nothing:
   - the executable is the **previous version** (the swap never happened, or the script just put it back): the database is put back from the copy if the new version had already changed its schema; the update is over (`failed`, or `rolled_back` when the database was put back);
   - the executable **cannot say its version or says another one**: the previous version and, if needed, the database are put back (`rolled_back`);
   - the executable is the **new version**: it is complete (it was synced before the swap) but was never watched. The start is counted in the marker and the marker stays for step 2. A new version that already had **two starts of the machine within an hour** and is still unconfirmed is taking the machine down, or never stays up long enough to be judged: the previous version is put back here, **before it runs a third time**. Starts that are further apart do not count (a marker that is still there days later means step 2 never ran, not that the machine cannot stay up: nothing is rolled back, and no data is lost, by counting).
2. **`regulus-update-confirm.service`, after Regulus started.** It runs `regulus update-apply --recover`, the same command as after a killed helper: the service is restarted and watched like in a normal update (active, the new version, up for 15 seconds within 90); healthy means the update stands (`applied`), otherwise the previous version and the database are put back (`rolled_back`).

So after a power cut the machine ends on the new version, checked, or on the previous one, and the Updates page shows which and why. It does not stay on a version that restarts in a loop. In the `automatic` mode a version that was put back is not tried again by itself, also when the cause was the power: install it from the Updates page.

**Limits.** These units come with the package: a server that was only ever updated from the dashboard since a version without them does not have them until the package is installed once (`install.sh`), see #254. If the copy of the previous version is missing or damaged as well, step 1 fails and says so in the journal (`journalctl -u regulus-update-recover`); the data is untouched and `install.sh` puts a working version back. None of this has run on a real machine yet: the `[Test]` issue for the update helper under faults (#240) has the steps.

## What a rollback puts back, and what it does not

If the new version does not come up healthy the helper puts the previous one back. A new version can **migrate the database at its first start**, and the previous version refuses a database with a migration it does not know ("created by a newer version"), so putting back only the program would leave a hub that cannot start. What is done depends on the database:

- **SQLite (the default).** Before it replaces the program the helper takes a consistent copy of `regulus.db` (`VACUUM INTO`, safe while the hub runs; kept in the root-owned state directory as `pre-update.db`, mode 0600, and removed when the update ends). If the update cannot be copied the **update is refused**, nothing is changed. On a rollback the helper stops the service and compares the schema version of the live database with the copy: **only if the schema moved** (or the database cannot be read) the copy is put back, with the old program; what the new version saved after the copy is then lost, and the result says so ("the database was put back from before the update"). If the schema did not move the database is kept as it is, with whatever was saved since.
- **PostgreSQL.** The helper cannot copy a database server, so it does **not** restore anything. **Make a backup before updating a hub that uses PostgreSQL** (`pg_dump`), and if an update that migrated the schema has to be undone, restore it by hand before the old version can start. Making rollbacks safe there (migrations the previous version can live with, a declared compatibility range instead of the strict check) is not done yet.
- **Agents** have no database; their rollback is only the program.

To try it on a real machine see the `[Test]` issue for the rollback after a migration.
