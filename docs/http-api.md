# HTTP API

`GET /api/agents` returns the connected agents as JSON (id, version, system info, `status` of `connected` or `stale`, last heartbeat, uptime). `GET /api/agents/{id}/metrics` returns the recent metrics of an agent (CPU, load, memory, swap, disks, network counters and rates, uptime), oldest first; `?since=<RFC 3339>` returns only newer points, `?step=<duration>` (`1s` to `1h`, such as `30s`) averages the reports into buckets of that length aligned to the Unix epoch, one point per bucket stamped with its newest report's time (CPU, load, memory and swap in use and the network rates are means; totals, uptime, disks and counters are the newest report's), and `?limit=<n>` returns only the newest n points (the dashboard asks for the last 600, enough for its 10-minute charts); they apply in the order since, step, limit. The hub keeps the last hour of metrics in memory (up to 3600 reports per agent, and about 256 MiB for all agents together, beyond which the oldest reports of any agent go first), so the history is lost when the hub restarts. Network rates are computed from the times the agent took the two reports (`collected_at`), not from when the hub received them, so a delayed or bunched delivery does not make a spike; a rate is left out (`null`) when the two reports are the same instant, out of order, or more than 5 minutes apart, and reports without `collected_at` (older agents) fall back to the receive times. `GET /api/agents/{id}` returns one agent. `GET /api/agents?all=true` also lists the enrolled agents that are `offline` or `revoked`, with the time the hub last heard from them (`last_seen_at`); `PATCH /api/agents/{id}` (`servers.manage`) gives an agent a display name. A connected agent also says what it cannot measure: `collector` is `linux` or `basic` (a system without /proc, which reports only the time and uptime), `unavailable` lists the parts of its last report it could not read (`cpu`, `load`, `memory`, `disks`, `network`, `uptime`; their numbers are zero and mean nothing, and each metrics point carries the same list), and `container` names the container it runs in, if any; all three are absent for an agent older than them ([Supported platforms](remote-agents.md#supported-platforms)). Every enrolled agent in these answers carries `cert_not_after` (RFC 3339), when its client certificate ends; it is absent for the built-in agent and, for an agent enrolled before the hub kept the date, until that agent next connects. `GET /api/certificates` (`servers.manage`) returns when the hub's certificates end: `ca`, `listener` (null while remote agents are off; it renews itself 30 days before its end), `soonest` (of all of them), `agents_unknown` (agents whose date the hub does not know yet), `warn_days` (90) and `warnings`, the CA and agent certificates (revoked agents left out) that end within 90 days or have ended, soonest first; each certificate is `{kind: "ca"|"listener"|"agent", agent_id?, name?, not_after, days_left}`. Neither the CA nor agent certificates are renewed automatically yet (#128): an agent is revoked and enrolled again, and a new CA means every agent enrolls again. `GET /api/plugins` (`servers.read`) returns the state of the plugins: `{"hub": {"enabled", "problem"?, "plugins": [...]}, "agents": [{"id", "name"?, "plugins": [...]}]}`, where each plugin is `{"id", "version", "state", "restarts", "last_error"?, "since"?}` and `state` is `starting`, `running`, `restarting`, `failed`, `incompatible`, `stopped` or `invalid` ([Plugin runtime](plugins/runtime.md)); an `invalid` entry is a directory in the plugins directory that is not a usable plugin (missing or invalid `plugin.yaml`, a name that is not the id, a symbolic link), with the directory name as `id`, an empty `version` and the reason in `last_error`; `hub.enabled` is false without `plugins_dir`, and `agents` lists only the connected agents that report a plugins directory, with what they sent with their last metrics. `GET /api/layout` and `PUT /api/layout` read and save the dashboard layout of the logged-in user (any JSON up to 64 KiB, stored per user). `GET /api/stream` upgrades to a **WebSocket** that pushes a `snapshot` of the agents and then `agent.connected`, `agent.disconnected`, `agent.heartbeat`, `agent.metrics` and `plugins.changed` events as JSON (`plugins.changed` has `source`, `hub` or `agent`, and the agent's `id`, and no state: the client reads `GET /api/plugins` again, as the Plugins page does); it needs the session cookie (rechecked every 30 seconds: the stream closes when the session ends or the user loses `servers.read`) and refuses pages from other origins, and a client that reads too slowly is disconnected and should reconnect. A user has at most 16 streams open at a time (one per dashboard tab); one more is refused with `429` until another closes. All of this is described in [`internal/hub/openapi.yaml`](../internal/hub/openapi.yaml), also served at `/api/openapi.yaml`; a test keeps the file in sync with the routes. The endpoints need a login and `GET`s are read-only; the dashboard shows the servers on the **Servers** page.
